## 1. Model Context Protocol in late 2026: revisions, interactive UI, host support, OpenAI Apps SDK, cheapest hosting, auth for a public read-only server

### Takeaway
The current specification is 2026-07-28, the largest revision since launch: MCP became a stateless request/response protocol (no handshake, no sessions), Tasks moved into an extension, Sampling/Roots/Logging and Dynamic Client Registration were deprecated, and extensions became a formal, versioned mechanism. MCP Apps (interactive HTML rendered by the host) is a Stable official extension supported by Claude web/desktop, ChatGPT, VS Code Copilot, Microsoft 365 Copilot, Cursor and Goose; a public read-only server may be authless under both the spec and Claude's and ChatGPT's connector rules, and can be hosted on the Cloudflare Workers free plan with a stateless handler.

### Cited Findings

#### Specification revisions and what each added
- 2025-06-18 (vs 2025-03-26): removed JSON-RPC batching; added structured tool output; classified MCP servers as OAuth resource servers with protected-resource metadata; required clients to implement RFC 8707 resource indicators; added elicitation; added resource links in tool results; required the `MCP-Protocol-Version` header on HTTP; added `title` fields and wider `_meta`. — [MCP changelog 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/changelog)
- 2025-11-25 (vs 2025-06-18): OpenID Connect discovery for authorization servers; icons for tools/resources/prompts; incremental scope consent; tool-naming guidance; URL-mode elicitation (SEP-1036); tool calling inside sampling (SEP-1577); OAuth Client ID Metadata Documents (CIMD) as the recommended registration mechanism (SEP-991); experimental Tasks for durable requests with polling (SEP-1686); JSON Schema 2020-12 as default dialect; input-validation errors to be returned as tool-execution errors so models can self-correct; governance changes (formal SEP process, working groups, SDK tiers). — [MCP changelog 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog)
- 2026-07-28 (vs 2025-11-25), major changes: protocol-level sessions and the `Mcp-Session-Id` header removed, list endpoints no longer vary per connection, cross-call state must use explicit server-minted handles passed as tool arguments (SEP-2567); the `initialize`/`initialized` handshake removed, each request carries protocol version and client capabilities in `_meta` (SEP-2575); new mandatory `server/discover` RPC; the HTTP GET stream and `resources/subscribe` replaced by a single opt-in `subscriptions/listen` stream; `ping`, `logging/setLevel` and roots list-changed removed; Tasks moved out of core into the `io.modelcontextprotocol/tasks` extension, redesigned around `tasks/get` polling plus `tasks/update` (SEP-2663); Multi Round-Trip Requests (MRTR) replace server-initiated `roots/list`, `sampling/createMessage` and `elicitation/create` — the server returns an `input_required` result and the client retries with `inputResponses` (SEP-2322); every result carries a required `resultType`; SSE resumability and `Last-Event-ID` removed. — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- 2026-07-28, minor changes: `extensions` field in client and server capabilities; OpenTelemetry trace-context keys in `_meta`; servers should return `tools/list` in deterministic order to help client and prompt caching; required `Mcp-Method`/`Mcp-Name` HTTP headers for routing; `ttlMs` and `cacheScope` on list and read results; looser `inputSchema`/`outputSchema` (any JSON Schema 2020-12 keyword) and `structuredContent` (any JSON value); authorization hardening (RFC 9207 `iss` validation, `application_type` at registration, credentials bound to the issuing authorization server). — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- 2026-07-28, deprecations: Roots, Sampling and Logging are deprecated (SEP-2577; suggested replacement for Sampling is to call LLM provider APIs directly); the old HTTP+SSE transport and Dynamic Client Registration (in favour of CIMD) are formally deprecated; a feature-lifecycle policy guarantees at least a twelve-month deprecation window. — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- The release post (28 July 2026) frames the motivation as reliability and scalability: any request can reach any server instance behind a plain load balancer; all four Tier-1 SDKs (TypeScript, Python, Go, C#) spoke the new revision on release day and Rust was in beta; Tier-1 SDKs see close to half a billion downloads a month. — [MCP blog, 2026-07-28 release](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Anthropic describes 2026-07-28 as the fifth spec release, says the stateless core lets servers run on serverless and edge infrastructure, said on release day that support would roll out across Claude products soon, without naming surfaces or dates, and reports more than 950 MCP servers in Claude's connectors directory. — [Claude blog: Bringing MCP 2026-07-28 to Claude](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude)
- Roadmap (last updated 2026-08-22): next priorities are agentic messaging (server-initiated events, webhooks, Tasks moving toward core), HTTP-native transport unification (HTTP over stdio, ETag-style caching), agent identity (DPoP, workload identity federation), improved primitives (a redesign of the `tools/call` result shape because simultaneous `content` and `structuredContent` confused implementers, plus "progressive discovery" of large tool sets), and generated SDKs. — [MCP roadmap](https://modelcontextprotocol.io/development/roadmap)
- Conflict: the official blog dates the release-candidate announcement to 18 June 2026, while a New Stack article says the RC was frozen on 21 May 2026 (search summary). — [MCP blog RC post](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/); [The New Stack](https://thenewstack.io/?p=22831200)

#### Extensions, MCP Apps and long-running work
- Official extensions and stages: MCP Apps (Stable), OAuth Client Credentials (Stable), Enterprise-Managed Authorization (Stable), Tasks (Beta, intended for core), Skills over MCP (Beta), Server Cards for HTTP discovery (Beta), Events (Beta). Experimental repositories cover interceptors, server variants, tool annotations, file uploads and filesystems. Extensions are always off by default, are negotiated through the `extensions` capability, and the guidance is to degrade gracefully (a UI-enhanced tool should still return meaningful text for hosts without the UI extension). — [MCP extensions overview](https://modelcontextprotocol.io/extensions/overview)
- MCP Apps mechanics: a tool's description carries `_meta.ui.resourceUri` pointing at a `ui://` resource; the host fetches the HTML (optionally preloading it), renders it in a sandboxed iframe, and talks to it over a JSON-RPC dialect on `postMessage` (`ui/initialize`, other `ui/*` methods, and `tools/call`); the app can call server tools, send messages, and update the model's context; `_meta.ui.csp` and `permissions` declare external origins and device capabilities; the `App` class in `@modelcontextprotocol/ext-apps` is optional sugar; the spec file is versioned `2026-01-26`. — [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview)
- MCP Apps became an official extension on 26 January 2026 (search summary). — [MCP blog, MCP Apps](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)
- The official examples include directly relevant 3D and data-visualisation apps: a CesiumJS globe (`map-server`), Three.js scenes (`threejs-server`), shader effects, cohort heatmaps, a PDF viewer, and starter templates for React, Vue, Svelte, Preact, Solid and vanilla JS. — [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview)
- The resource MIME type is `text/html;profile=mcp-app`. — [OpenAI: MCP Apps in ChatGPT](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt)
- Host builders can use `@mcp-ui/client` or the SDK's AppBridge module; MCP-UI describes itself as standardised into MCP Apps, with its packages now implementing that spec (Apache-2.0) and a legacy adapter for old MCP-UI content. — [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview); [mcpui.dev](https://mcpui.dev/)

- OpenAI states that ChatGPT implements the open MCP Apps standard; `window.openai` remains as compatibility aliases plus ChatGPT-only extensions (checkout, file upload/selection, modal requests, widget state). - OpenAI's developer docs now frame the product as "plugins" bundling skills, MCP servers and optional UI, running in ChatGPT and Codex, with review before listing in the ChatGPT directory; the `window.openai` APIs are labelled legacy. The Apps SDK changelog lists MCP Apps compatibility under February 2026 (search summary). — [OpenAI Apps SDK docs](https://developers.openai.com/apps-sdk/); [Apps SDK changelog](https://developers.openai.com/apps-sdk/changelog)

#### Registry
- The official MCP Registry is still labelled preview, with a warning that breaking changes or data resets may happen before general availability. It stores metadata only (`server.json` pointing at npm/PyPI/Docker packages or a remote URL), verifies namespaces via GitHub, DNS or HTTP challenges, supports public servers only, and is meant to be consumed by downstream aggregators rather than directly by host applications. — [MCP Registry: about](https://modelcontextprotocol.io/registry/about)

#### Cheapest way to build and host a remote server
- Cloudflare's current guide builds remote servers with `createMcpHandler` from the Agents SDK: stateless, a fresh `McpServer` per request, no Durable Object required; a public template exists (`cloudflare/ai/demos/remote-mcp-authless`, created with `npm create cloudflare@latest -- remote-mcp-server-authless --template=cloudflare/ai/demos/remote-mcp-authless`); OAuth is added with the Workers OAuth Provider library (GitHub, Google, Cloudflare Access or a custom identity provider). — [Cloudflare: Build a remote MCP server](https://developers.cloudflare.com/agents/guides/remote-mcp-server/)
- Agents SDK v0.20.0 marks the older `McpAgent` class deprecated and feature-frozen; the migration pairs `agents` 0.20.0 with `@modelcontextprotocol/server` 2.3.1 for stateless servers and keeps `@modelcontextprotocol/sdk` 1.32.1 only for a temporary legacy lane; sessions, standalone GET streams and pushed sampling/elicitation are legacy features. — [Cloudflare: Migrate to MCP SDK v2](https://developers.cloudflare.com/agents/model-context-protocol/guides/migrate-to-mcp-sdk-v2/)
- Workers Free plan: 100,000 requests per day and 10 ms CPU per invocation; the paid plan starts at US$5 per month. Free allowances also exist for SQLite Durable Objects, KV, D1 (5 GB, 5 million rows read per day) and R2 (10 GB). — [Cloudflare Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)
- TypeScript SDK: v2.4.0 was the latest release (23 October), split into `@modelcontextprotocol/client`, `server`, `core`, `server-legacy` and a codemod, with a parallel v1 line at 1.32.2; release notes say features work on both 2025-11-25 and 2026-07-28. — [typescript-sdk releases](https://github.com/modelcontextprotocol/typescript-sdk/releases)
- Python: FastMCP 4 is generally available; it removes `ctx.sample()` and `ctx.list_roots()`, serves the sessionless protocol so any replica can answer, and keeps handshake-era clients working. — [FastMCP v4 notes](https://gofastmcp.com/development/v4-notes.md)
- Vercel's `mcp-handler` announced support for the latest spec (changelog title seen in search results only). — [Vercel changelog](https://vercel.com/changelog/latest-mcp-spec-now-supported-in-mcp-handler-4jLhfbd5qlwkl2lcu5R2oU)

#### Auth options for a public, read-only server
- The 2026-07-28 spec says authorization is optional for MCP implementations. When used over HTTP it is OAuth 2.1 with mandatory protected-resource metadata (RFC 9728), CIMD recommended, Dynamic Client Registration optional and deprecated, resource indicators (RFC 8707) on every authorization and token request, and no tokens in query strings. — [MCP authorization spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Claude supports six connector auth types: OAuth with DCR, OAuth with CIMD, OAuth with Anthropic-held client credentials, credentials entered at connection time (by arrangement), static request headers (beta, limited organisations) and `none` (authless, supported by default). "Lazy authentication" lets public tools run immediately and defers sign-in until a protected tool is called. Claude recommends CIMD or Anthropic-held credentials over DCR for high-traffic servers because DCR registers a new client on every fresh connection. Claude's outbound traffic comes from `160.79.104.0/21`. — [Claude docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)
- ChatGPT: anonymous read-only servers are supported; each tool can declare `noauth` or `oauth2` security schemes; OAuth requires protected-resource metadata and PKCE S256, with CIMD preferred over DCR. — [OpenAI: plugin/app authentication](https://developers.openai.com/apps-sdk/build/auth)

### Inferences
- What changed during 2026 (flag for the report): MCP Apps became official (January); ChatGPT aligned with it (February); the stateless 2026-07-28 spec shipped (July); Cloudflare deprecated `McpAgent` in favour of stateless handlers; TypeScript SDK v2 and FastMCP 4 became the current lines; Sampling, Roots, Logging and DCR entered deprecation.
- Cheapest viable design: one stateless, authless Streamable-HTTP server on the Workers free plan (TypeScript SDK v2 + `createMcpHandler`), reading a pre-built dataset from static assets/R2/D1. Statelessness in the 2026 spec makes free serverless hosting first-class rather than a workaround. A Python alternative (FastMCP 4 mounted in the existing FastAPI app) is functionally fine but needs an always-on host, which fights the $0 target.
- For a public read-only server, choose `none` auth and protect it with edge rate limiting and response caching (`ttlMs`/`cacheScope` are designed for this). If per-user features appear later, add lazy OAuth with CIMD; avoid DCR.
- Do not design around MCP Sampling as a way to borrow the host's model for free: it is deprecated in the spec and Claude never supported it. Treat elicitation as optional too (MRTR-only from 2026-07-28, uneven host support).
- Serve both protocol eras for at least a year: Claude's connector docs still reference the 2025-era authorization specs and its 2026-07-28 rollout status is unconfirmed; the current SDKs handle dual-mode serving.
- Design every tool to be useful without UI (text plus `structuredContent`), then attach MCP App views for the hosts that render them. Claude Code and other terminal hosts will never show the 3D map or the structure viewer.
- MCP Apps is the route by which the app's own views (protein map, Mol* viewer, knowledge graph) can appear inside Claude, ChatGPT, VS Code and Cursor. Claude's "app tools" are the closest external analogue to the existing "interface moves before it speaks" behaviour, but they are gated, web-only and approval-prompted, so they are a bonus, not a foundation.
- Build to the MCP Apps standard first and treat OpenAI's `window.openai` extras as optional progressive enhancement; the OpenAI "Apps SDK" is now effectively a ChatGPT-flavoured profile of MCP Apps.
- The registry's preview status means listing is cheap but not a distribution strategy; host-specific directories (Claude connectors directory, ChatGPT directory) are where discovery actually happens, and both involve review.
- Skills over MCP (Beta) could let the server ship short workflow instructions ("how to investigate a target") to hosts that support it (Claude web, Claude Code, VS Code).

## 2. Biology and life-science MCP servers and tool libraries: status, licence, quality, reuse versus wrap

### Takeaway
There is one clearly official, well-designed database server (Open Targets, January 2026) and two actively maintained broad libraries (BioMCP, now a Rust binary; ToolUniverse, now thousands of tools), but EMBL-EBI had not shipped official servers for UniProt, PDBe, AlphaFold DB, Europe PMC or Ensembl as of its last public statement, and the popular community per-database servers look dormant. Anthropic's own life-science stack has moved from individual connectors to bundled, read-only, keyless "Featured connectors" inside a separate Claude Science product, which is a useful design reference rather than something a third-party app can reuse.

### Cited Findings
- Open Targets (official): announced 12 January 2026, built with FastMCP on the public GraphQL API, available in Claude; hosted endpoint `https://mcp.platform.opentargets.org/mcp`; five tools (`get_open_targets_graphql_schema` for category-based schema subsets, `get_type_dependencies`, `query_open_targets_graphql`, `batch_query_open_targets_graphql`, `search_entities` for ID resolution); optional jq filtering to cut tokens; the README still calls it experimental and under active development. — [Open Targets blog](https://blog.opentargets.org/official-open-targets-mcp/); [platform-mcp README](https://raw.githubusercontent.com/opentargets/platform-mcp/main/README.md)
- Open Targets' own benchmarking (their "Karenina" framework, 140 question–answer pairs across models, agent architectures and official versus third-party servers) found that generic API wrappers struggle with complex aggregations, multi-entity queries and result interpretation, causing wasteful workflows, heavy token use and more errors; no accuracy figures were published in the post. — [Open Targets blog](https://blog.opentargets.org/official-open-targets-mcp/)
- BioMCP (GenomOncology): MIT; 685 stars; a single binary reaching 72 biomedical sources (PubMed, ClinVar, ClinicalTrials.gov, OncoKB, Reactome and others) with 13 "gettable" entity types (gene, variant, article, trial, drug, disease, pathway, protein and more); runs as a CLI, a stdio MCP server (`biomcp serve`) or a remote HTTP server (`biomcp serve-http`, endpoint `/mcp`); installed as `biomcp-cli` (the PyPI package named `biomcp` is unrelated); most commands need no credentials. — [BioMCP repository](https://github.com/genomoncology/biomcp)
- BioMCP was rewritten from Python to Rust at v0.8.0; the Python line ended at 0.7.3, `biomcp-python` is unmaintained, and MCP tool names and signatures changed (search summary of the project changelog and release discussion). — [BioMCP changelog mirror](https://glama.ai/mcp/servers/@genomoncology/biomcp/blob/ca013a965c88a3d37a63cde9af00456c91b0cced/docs/changelog.md)
- BioContextAI: a community registry of biomedical MCP servers plus a "Knowledgebase MCP" (Apache-2.0 code, 33 stars) exposing Antibody Registry, bioRxiv/medRxiv, Ensembl, Europe PMC, Google Scholar, InterPro, KEGG, Open Targets, PanglaoDB, PRIDE, Protein Atlas, Reactome, STRING and AlphaFold DB, generated largely from OpenAPI specs with FastMCP; a hosted endpoint exists but is described as for testing only under fair use; Google Scholar and KEGG are local-only for rate-limit and licence reasons, and KEGG prohibits commercial or remotely hosted use. — [BioContextAI knowledgebase-mcp](https://github.com/biocontext-ai/knowledgebase-mcp)
- The BioContextAI paper appeared in Nature Biotechnology (Kuehl et al., published 6 November 2025). EMBL's accompanying interview (2 December 2025) says EMBL-EBI is exploring MCP for its resources, names no official EMBL-EBI server, notes most servers in the registry are third-party, and lists security, sustainability of hosted servers, metadata standards, licensing and discoverability as open problems. — [EMBL news](https://www.embl.org/news/people-perspectives/connecting-ai-to-biology-model-context-protocol/)
- ToolUniverse (Harvard MIMS, Zitnik lab): repository licence Apache-2.0; about 1.8k stars; README now claims more than 2,700 models, datasets, APIs and packages; ships as a local MCP server (`uvx tooluniverse`), a CLI, a Python SDK, 154 research skills and a Claude Code plugin; a "compact mode" exposes only 4–5 discovery tools and is said to save about 99% of the context window; results are cached in memory and SQLite; no hosted endpoint is mentioned. — [ToolUniverse repository](https://github.com/mims-harvard/ToolUniverse)
- ToolUniverse counts conflict by date and source: 211 tools at launch (June 2025), more than 600 in Anthropic's January 2026 announcement, and more than 1,000 in current docs (search summary); the lab's licence page reportedly names MIT while including Apache-2.0 text (search summary). — [Zitnik lab, June 2025](https://zitniklab.hms.harvard.edu/2025/06/03/ToolUniverse); [Anthropic, January 2026](https://www.anthropic.com/news/healthcare-life-sciences); [ToolUniverse licence page](https://zitniklab.hms.harvard.edu/ToolUniverse/about/license.html)
- Biomni's library: Apache-2.0 code with an explicit warning that integrated tools, databases and software may carry more restrictive commercial licences; about 4.1k stars; an optional data lake of roughly 11 GB; a "Know-How Library" of protocols; MCP client (`add_mcp()`) and server examples; it executes model-generated code with full system privileges and recommends sandboxing. — [Biomni repository](https://github.com/snap-stanford/Biomni)
- Anthropic connectors: existing by January 2026 — Benchling, 10x Genomics, PubMed, BioRender, Synapse.org, Wiley Scholar Gateway; added 11 January 2026 — Medidata, ClinicalTrials.gov, ToolUniverse, bioRxiv & medRxiv, Open Targets, ChEMBL, Owkin; skills added — scientific problem selection, instrument data to Allotrope, scVI-tools, Nextflow, clinical trial protocol drafting. — [Anthropic: healthcare and life sciences](https://www.anthropic.com/news/healthcare-life-sciences)
- Claude Science (beta desktop app) bundles "Featured connectors" that are on by default, read-only and need no account or key: Ensembl (with VEP), MyGene, UniProt, GO, Reactome, OLS, gnomAD, ClinVar, dbSNP, GWAS Catalog, FinnGen, BioBank Japan, ClinGen, CIViC, Open Targets, GTEx, JASPAR, UniBind, InterPro, Pfam, Human Protein Atlas, STRING, PDB, AlphaFold, EMDB, Complex Portal, IntAct, Rfam, GEO, ArrayExpress, PRIDE, MGnify, MetaboLights, cBioPortal, PubChem, ChEBI, Rhea, BindingDB, FDA/openFDA, OpenAlex, arXiv and others; four directory connectors (PubMed, Clinical Trials, ChEMBL, bioRxiv); featured skills for literature review and for models including AlphaFold2, Boltz-2, Chai-1, ESMFold2, OpenFold3, ProteinMPNN, DiffDock, ESM-2 and Evo 2. The docs warn that some underlying databases have non-commercial or attribution terms. — [Claude Science: connectors and skills](https://claude.com/docs/claude-science/connectors-and-skills.md)
- Anthropic's `life-sciences` GitHub repository has been refocused on skills and no longer hosts MCP connector plugins; current skills are clinical-trial-protocol, scientific-problem-selection, clinical-trial-forecast and binder-gauntlet (computational validation of designed binders). — [anthropics/life-sciences](https://github.com/anthropics/life-sciences)
- Community per-database servers (Augmented-Nature organisation): JavaScript servers for ChEMBL (89 stars), PubChem (49), PDB (28), Reactome, Open Targets, Ensembl (4), STRING and others, with UniProt and AlphaFold servers listed in the README; every visible repository was last updated on 21 December 2025 and no 2026 activity was evident. — [Augmented-Nature on GitHub](https://github.com/Augmented-Nature)
- Other community packages seen: `pdbe-mcp-server` on PyPI (maintainer not confirmed), an "EMBL-EBI protein MCP" explicitly marked unofficial, and a community `uniprot-mcp-server` (search summary). — [pdbe-mcp-server on PyPI](https://pypi.org/project/pdbe-mcp-server)
- Upstream API limits matter when wrapping directly: Ensembl REST allows 55,000 requests per hour (about 15 per second) and answers HTTP 429 with `Retry-After` when exceeded. — [Ensembl REST rate limits](https://github.com/Ensembl/ensembl-rest/wiki/Rate-Limits)

### Inferences
- Reuse-or-wrap verdicts: Open Targets — reuse the official hosted server for agent hosts and copy its design; BioMCP — credible optional add-on (clinical and variant coverage) but a moving target after the Rust rewrite; ToolUniverse — excellent as a user-installed local server for power users, too large and fast-changing to be a dependency; BioContextAI KB — good reference implementation, hosted endpoint not suitable for production; Augmented-Nature servers — do not depend on them; UniProt, RCSB PDB, AlphaFold DB, ChEMBL, Europe PMC, Ensembl — wrap the REST APIs directly (or better, pre-ingest into the app's own dataset) because no official servers were found and the APIs are stable and free.
- The Open Targets tool design is the best template for the app's own server: a few schema-exploration tools returning focused subsets, one validated query tool, one batch tool, one entity-resolution tool, optional server-side filtering to cut tokens. It directly encodes their finding that one-tool-per-endpoint wrappers perform badly.
- Anthropic's Featured-connector list is effectively a map of which public biology databases a serious agent is expected to reach; the app's 2.0 dataset and live tools can be prioritised against it (UniProt, AlphaFold, PDB, Open Targets, ChEMBL, Reactome, STRING, InterPro, ClinVar/gnomAD, GTEx, Europe PMC/PubMed).
- Licensing is a real design constraint: redistributing or remotely serving some sources (KEGG explicitly) is not allowed, so the public server should expose only sources with open terms and record per-source licence and attribution in tool output.
- A "bring your own MCP servers" setting in the app (user connects BioMCP or ToolUniverse locally) adds breadth at zero hosting cost without taking on their maintenance risk.

### Gaps

## 3. Leading scientific agents: architectures, evaluations, and what fails

### Takeaway
The successful systems converge on the same skeleton: an orchestrator over specialised sub-agents, code execution as the main action space, retrieval over a large tool catalogue instead of loading it all, generate–critique–rank loops, and claim-level traceability to code or literature. Their own evaluations show the ceiling clearly: roughly four in five statements correct for the best autonomous system, far lower on database-lookup and sequence tasks without tools, sub-human results on end-to-end biomedical ML tasks, and domain specialisation mattering less than scaffolding.

### Cited Findings

#### Systems
- Biomni (Stanford): a general-purpose biomedical agent that combines LLM reasoning with retrieval-augmented planning and code-based execution rather than fixed workflows; its action space was mined from tens of thousands of publications across 25 domains; the abstract reports generalisation to causal gene prioritisation, drug repurposing, rare-disease diagnosis, microbiome analysis and cloning without task-specific prompts but gives no benchmark numbers. Open source under Apache-2.0, with a free web interface at biomni.stanford.edu, a reasoning model (Biomni-R0, built on Qwen-32B with reinforcement learning) and a 433-item, 10-task benchmark (Biomni-Eval1). — [Biomni preprint](https://www.biorxiv.org/content/10.1101/2025.05.30.656746v1); [Biomni repository](https://github.com/snap-stanford/Biomni)
- Phylo sells "Biomni Lab" as a commercial collaborative workspace with 100+ prebuilt workflows and an enterprise edition; its page says agents check reasoning against a biology knowledge graph. — [Phylo](https://phylo.bio/)
- PaperQA2 (FutureHouse, September 2024): a literature agent optimised for factuality that matches or exceeds subject-matter experts on three literature tasks, exceeds humans on the LitQA2 benchmark, writes cited summaries judged more accurate than existing Wikipedia articles, and finds 2.34 ± 1.99 contradictions per paper of which experts validated 70%. — [PaperQA2 on arXiv](https://arxiv.org/abs/2409.13740)
- Robin (FutureHouse, May 2025): a workflow over three agents — Crow (literature), Falcon (candidate evaluation), Finch (data analysis) — that generated hypotheses, chose experiments, analysed data and produced the figures, while humans ran the physical experiments; it proposed ripasudil for dry age-related macular degeneration and identified ABCA1 upregulation; the work was later published in Nature (page updated 19 May 2026); results are preclinical cell-culture findings. — [FutureHouse: Robin](https://www.futurehouse.org/research/demonstrating-end-to-end-scientific-discovery-with-robin-a-multi-agent-system); [Robin on arXiv](https://arxiv.org/abs/2505.13400)
- Kosmos (Edison Scientific, the FutureHouse spin-out; November 2025): a structured world model shares state between a data-analysis agent and a literature agent across about 200 agent rollouts; runs last up to 12 hours, execute on average 42,000 lines of code and read about 1,500 papers; every report statement is linked to code or primary literature; independent scientists judged 79.4% of statements accurate; collaborators estimated one 20-cycle run equalled about six months of their own work; seven discoveries are reported, three reproducing unpublished findings and four described as novel. — [Kosmos on arXiv](https://arxiv.org/abs/2511.02824)
- Kosmos limitations stated by its authors: it goes down rabbit holes, chases statistically significant but scientifically irrelevant findings, users often run it several times per objective, and the time-saved estimates are acknowledged as inherently suspect; launch pricing was US$200 per run. — [Edison: Announcing Kosmos](https://edisonscientific.com/news/announcing-kosmos)
- Edison in 2026: partnerships or agreements with Incyte (May), Population Health Partners (June), Springer Nature (September) and Pfizer (October); the product is positioned as model-agnostic and deployable on-premises. A US$70 million raise was reported in December 2025 (search summary). — [Edison news index](https://edisonscientific.com/blog); [Edison home page](https://edisonscientific.com/); [SiliconANGLE](https://siliconangle.com/?p=725574)
- Google Co-Scientist: published in Nature on 19 May 2026; a Gemini-based multi-agent system with Generation, Proximity (clustering for diversity), Reflection (virtual peer review), Ranking (Elo tournament of pairwise debates), Evolution and Meta-review agents under a supervisor that plans and parallelises; verification uses web search and databases such as ChEMBL and UniProt, with AlphaFold in trials; reported validations include a liver-fibrosis repurposing candidate and a confirmed ageing-biology hypothesis; individual access is through an experimental "Hypothesis Generation" tool in Gemini for Science; Google says it had internal, external and independent CBRN-misuse evaluations and uses custom classifiers to flag unethical research goals, and that it is not a replacement for scientific or clinical expertise. — [Google DeepMind: Co-Scientist](https://deepmind.google/blog/co-scientist-a-multi-agent-ai-partner-to-accelerate-research/); [Nature paper](https://www.nature.com/articles/s41586-026-10644-y)
- TxAgent (Harvard, March 2025): therapeutic reasoning over a toolbox of 211 tools (ToolUniverse) drawing on FDA drug data and Open Targets; reports 92.1% accuracy on open-ended drug-reasoning tasks across five new benchmarks (3,168 tasks, 456 personalised scenarios) and outperforming GPT-4o and DeepSeek-R1 on those benchmarks. — [TxAgent on arXiv](https://arxiv.org/abs/2503.10970)
- CRISPR-GPT: an LLM agent with domain knowledge and tools that automates CRISPR system selection, guide design, delivery choice, protocol drafting and validation design, validated in a real use case; the paper discusses ethical and regulatory considerations for automated gene-editing design. — [CRISPR-GPT on arXiv](https://arxiv.org/abs/2404.18021)
- STELLA (July 2025): a self-evolving multi-agent system with a growing template library of reasoning strategies and a "Tool Ocean" extended by a tool-creation agent; reports about 26% on the biomedicine portion of Humanity's Last Exam and 54% / 63% on LAB-Bench DBQA / LitQA, with accuracy nearly doubling as experience accumulates. — [STELLA on arXiv](https://arxiv.org/abs/2507.02004)
- Claude Science (Anthropic, beta in 2026): a desktop workbench where Claude writes and runs Python, R or shell in a local sandbox, pulls from database connectors, stores results as versioned artefacts with provenance, and a background "reviewer" checks claims against the execution record; Anthropic states the reviewer reduces but does not eliminate errors and does not re-run analyses, and that the product is not for clinical or diagnostic use. — [Claude Science overview](https://claude.com/docs/claude-science/overview)

#### What the evaluations show
- BixBench (FutureHouse): real bioinformatics analysis scenarios; with 2025 frontier models (GPT-4o, Claude 3.5 Sonnet) open-answer accuracy was only 17% and multiple-choice performance was no better than random. — [BixBench on arXiv](https://arxiv.org/abs/2503.00096)
- BioML-bench: on end-to-end biomedical ML tasks (protein engineering, single-cell omics, imaging, drug discovery) four agents (STELLA, Biomni, AIDE, MLAgentBench) on average underperformed human baselines; biomedical specialisation gave no consistent advantage, and agents using more diverse ML strategies did best, suggesting scaffolding matters more than domain specialisation. — [BioML-bench preprint](https://www.biorxiv.org/content/10.1101/2025.09.01.673319v1)
- LABBench2 scores reported for GPT-5.2 vary enormously by task and tooling: 0.799 on literature QA with tools, 0.525 on figure QA, 0.447 on protocol QA (agentic), 0.286 on cloning, 0.115 on sequence QA and 0.058 on database QA without tools. — [Inspect Evals: LAB-Bench 2](https://ukgovernmentbeis.github.io/inspect_evals/evals/lab_bench_2/index.html)
- ScienceAgentBench: the best agent solved 32.4% of 102 data-driven discovery tasks independently (34.3% with expert knowledge); o1-preview reached 42.2% at more than ten times the cost. — [ScienceAgentBench on arXiv](https://arxiv.org/abs/2410.05080)
- FutureHouse argued in July 2025 that a large share of the chemistry and biology answers in Humanity's Last Exam are likely wrong, a caution about label noise in headline benchmarks. — [FutureHouse research index](https://www.futurehouse.org/research-announcements)

### Inferences
- Shared architectural patterns worth copying at small scale: (1) code or query execution over data as the primary action, with only summaries returned to the model; (2) search over the tool catalogue rather than a giant tool list; (3) a deterministic entity-resolution and verification layer (Co-Scientist checks against ChEMBL/UniProt; Phylo checks against a knowledge graph); (4) a separate critic/reviewer pass that checks claims against what was actually executed; (5) claim-level provenance surfaced in the UI; (6) explicit persistent state (Kosmos's world model) instead of relying on the transcript.
- What fails, in order of relevance to this app: database lookups from model memory (near zero without tools); long autonomous runs drifting into irrelevant but statistically "significant" findings; one-in-five wrong statements even in the best system; self-reported productivity claims; and unsandboxed code execution. A grounded-first design with typed tools attacks the first and third directly.
- For a portfolio project the honest positioning is "grounded explorer with multi-step tool use", not "AI scientist": the systems that claim discoveries rely on wet-lab partners, hours-long runs and budgets (Kosmos at US$200 per run) far outside a $0–20 per month envelope.
- The BioML-bench result (scaffolding over specialisation) supports spending effort on tool design, state and verification rather than on a biology-specific model.

### Gaps
- The Stanford Virtual Lab could not be read in this session: the Nature page ([s41586-025-09442-9](https://www.nature.com/articles/s41586-025-09442-9)) redirects to an authentication bounce and the bioRxiv abstract ([2024.11.11.623004](https://www.biorxiv.org/content/10.1101/2024.11.11.623004v1)) was refused by the fetch tool's own safety classifier. From memory (unverified): a principal-investigator agent runs "meetings" of specialist scientist agents plus a critic, with light human guidance, and built an ESM / AlphaFold-Multimer / Rosetta pipeline that designed 92 nanobodies against recent SARS-CoV-2 variants, a few of which bound in experiments.
- No independent audit of Kosmos's accuracy claim was found; the 79.4% figure is from the developers' own paper.
- Biomni's quantitative benchmark results and tool counts were not in the abstract.
- 2026 systems I could not research after the search budget ran out: OpenAI's life-science offerings, K-Dense, newer FutureHouse/Edison agents and benchmarks, and any 2026 successors to STELLA, TxAgent or CRISPR-GPT.
- Current frontier-model scores on BixBench (including any "verified" subset) were not found; the 17% figure is from early 2025 models.

## 4. Agent frameworks (TypeScript at the edge, or Python) and running the whole loop in the browser with a user-supplied key

### Takeaway
For a TypeScript front end the Vercel AI SDK (now major version 7) is the most complete provider-neutral option, with first-class client-executed tools, typed tool parts for UI, tool approvals and an in-process transport; Pydantic AI is the strongest fit for the existing Python backend and speaks both AG-UI and the Vercel AI stream format. A fully in-browser loop with a user's own key is technically supported by Anthropic (opt-in CORS header), the OpenAI SDK (opt-in flag) and OpenRouter (purpose-built PKCE flow), is explicitly discouraged by Google for Gemini, and shifts all key-theft risk onto the app's XSS hygiene.

### Cited Findings

#### Frameworks
- Claude Agent SDK: Claude Code packaged as a Python/TypeScript library with built-in file, shell and web tools, hooks, subagents, MCP, permissions, sessions and skills; each session spawns a `claude` CLI subprocess with local disk state, so hosting needs roughly 1 GiB RAM, 5 GiB disk and 1 CPU per agent in a container; use is governed by Anthropic's Commercial Terms, third-party products may not offer claude.ai login or subscription rate limits, and "Claude Code" branding is not permitted. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview); [Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting)
- Anthropic API client SDK (TypeScript): Apache-2.0 (older releases MIT); runs on Node 20+, Deno, Bun, Cloudflare Workers, Vercel Edge and, opt-in via `dangerouslyAllowBrowser`, in browsers; the SDK's beta tool runner drives the tool loop for tools you define (it is a helper over the Messages API, not the Agent SDK). — [anthropic-sdk-typescript](https://github.com/anthropics/anthropic-sdk-typescript); [Agent SDK overview (comparison table)](https://code.claude.com/docs/en/agent-sdk/overview)
- Vercel AI SDK: AI SDK 7 was announced on 25 June 2026; release notes on 24 November reference `ai@7.0.181`; migration guides exist for 5→6 and 6→7 with a codemod (`npx @ai-sdk/codemod v7`). Version 7 adds a unified `reasoning` option, typed runtime context for `ToolLoopAgent`, per-tool approvals with optional HMAC signing, timeouts at several levels, an OpenTelemetry-based telemetry redesign, `WorkflowAgent` for durable resumable runs, an experimental `HarnessAgent` that drives Claude Code, Codex or Pi, provider file and skill uploads, and an `MCPAppRenderer` component that renders MCP Apps in sandboxed iframes. — [Vercel: AI SDK 7](https://vercel.com/blog/ai-sdk-7); [vercel/ai releases](https://github.com/vercel/ai/releases); [AI SDK migration guides](https://ai-sdk.dev/docs/migration-guides)
- AI SDK tool model in `useChat`: three kinds of tool — server-executed, client-executed automatically through `onToolCall` plus `addToolOutput`, and user-interaction tools whose result the UI supplies; `sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls` resubmits when results are in; tool calls arrive as typed message parts named `tool-<name>` with states (`input-streaming`, `input-available`, `output-available`, `output-error`, plus approval states); unknown tools (for example MCP tools without schemas) appear as `dynamic-tool`; approvals use `toolApproval` on the server and `addToolApprovalResponse` in the UI (`needsApproval` is deprecated); multi-step loops are bounded with `stopWhen: isStepCount(n)`. — [AI SDK: chatbot tool usage](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-tool-usage)
- AI SDK transports: `DefaultChatTransport` (HTTP POST), `WebSocketChatTransport`, `WorkflowChatTransport`, and `DirectChatTransport`, which runs an agent in-process with no HTTP endpoint (documented for server-side rendering, tests and single-process apps; no stream reconnection). — [AI SDK: transport](https://ai-sdk.dev/docs/ai-sdk-ui/transport)
- The AI SDK's Anthropic provider exposes tool search, code execution and programmatic tool calling, the MCP connector, web search/fetch, citations, cache-control breakpoints (5-minute or 1-hour), context management and compaction, and accepts custom `headers` and `fetch`. — [AI SDK Anthropic provider](https://ai-sdk.dev/providers/ai-sdk-providers/anthropic)
- Pydantic AI: MIT; 21.4k stars; model-agnostic (OpenAI, Anthropic, Google, Bedrock, Groq, Mistral, xAI, Ollama and more) with fallback models; emits AG-UI and Vercel AI event streams for front ends; human-in-the-loop via deferred tools; typed, validated outputs; durable execution on nine engines (Temporal, DBOS, Prefect, Restate and others); Pydantic Evals grades outputs and tool-call trajectories; OpenTelemetry-native. — [Pydantic AI overview](https://pydantic.dev/docs/ai/overview/); [pydantic-ai repository](https://github.com/pydantic/pydantic-ai)
- LangGraph: MIT; 45.4k stars; durable execution, human-in-the-loop state inspection, short- and long-term memory; a JS/TS equivalent exists; "Deep Agents" is a higher-level package built on it. — [LangGraph repository](https://github.com/langchain-ai/langgraph)
- Mastra: Apache-2.0 for the core with a separate enterprise licence for `ee/` directories; 29.8k stars; agents, graph workflows with suspend/resume for human approval, memory, MCP server authoring, built-in evals and observability, 40+ model providers, and integrations with AI SDK UI and CopilotKit. — [Mastra repository](https://github.com/mastra-ai/mastra)
- OpenAI Agents SDK (JS): MIT; about 4.0k stars; Node 22+, Deno and Bun, with Cloudflare Workers marked experimental; described as provider-agnostic; handoffs, guardrails, human-in-the-loop, sessions, tracing, MCP and hosted tools; browser use is documented only for realtime voice with server-issued ephemeral tokens. — [openai-agents-js](https://github.com/openai/openai-agents-js)
- Cloudflare Agents SDK: MIT; 6.1k stars; agents are stateful Durable Objects with automatic state sync to connected clients, typed RPC, scheduling, MCP client and server roles, durable workflows with approval, React hooks (`useAgent`, `useAgentChat`) and "Code Mode"; requires a SQLite Durable Object binding. — [cloudflare/agents](https://github.com/cloudflare/agents)
- TanStack AI: a TypeScript SDK with provider adapters (OpenRouter, OpenAI, Anthropic, Gemini, Ollama), "isomorphic" tools that can run on the server or in the browser, tool approval, and hooks for React, Vue, Solid, Svelte and Angular; no hosting vendor required; an MCP Apps guide exists under its v0 docs (search result). — [TanStack AI overview](https://tanstack.com/ai/latest/docs/getting-started/overview); [TanStack AI MCP Apps](https://tanstack.com/ai/v0/docs/mcp/apps)
- AG-UI lists first-party or partner integrations for LangGraph, CrewAI, Microsoft Agent Framework, Google ADK, AWS Strands, Mastra, Pydantic AI, Agno, LlamaIndex and AG2, and community integrations for the Claude Agent SDK, OpenAI Agents SDK and Cloudflare Agents. — [AG-UI introduction](https://docs.ag-ui.com/introduction)

#### Direct browser access with a user-supplied key
- Anthropic enabled CORS on its API in August 2024 behind the request header `anthropic-dangerous-direct-browser-access: true`; the legitimate uses named are internal tools for trusted users and bring-your-own-key apps; the risk named is that any key embedded in client code can be extracted. — [Simon Willison, 23 Aug 2024](https://simonwillison.net/2024/Aug/23/anthropic-dangerous-direct-browser-access/)
- The OpenAI Node SDK supports browsers only with `dangerouslyAllowBrowser: true`, warns that this exposes secret credentials in client code, and lists lower-risk cases (internal tools, low-privilege credentials, short-lived debugging keys). — [openai-node](https://github.com/openai/openai-node)
- Google tells developers never to expose Gemini API keys client-side in production and recommends a backend proxy, plus key restrictions and billing alerts. — [Google AI Studio: API keys](https://aistudio.google.com/docs/api-key)
- OpenRouter offers an OAuth PKCE flow designed for client apps: redirect the user to `https://openrouter.ai/auth` with a callback and S256 challenge, exchange the code at `https://openrouter.ai/api/v1/auth/keys` (the docs' example does this with a browser `fetch`), and receive a user-controlled key; the user can set a dollar credit limit and an expiry on that key; codes are single-use and expire in 10 minutes. Its storage guidance is strict: encrypted server-side storage or an OS keychain, never `localStorage`, `sessionStorage`, IndexedDB or script-readable cookies. — [OpenRouter OAuth PKCE](https://openrouter.ai/docs/use-cases/oauth-pkce)
- Anthropic's key guidance: keep keys out of code, rotate (for example every 90 days), use separate keys per environment, set spend limits and workspace rate limits; keys found in public GitHub repositories are automatically deactivated through GitHub's secret-scanning partnership. — [Anthropic: API key best practices](https://support.claude.com/en/articles/9767949-api-key-best-practices-keeping-your-keys-safe-and-secure)

### Inferences
- What changed during 2026: AI SDK went from 6 to 7 (agents, approvals, durable workflows, MCP Apps rendering); AG-UI and A2UI reached 1.0; Anthropic's TypeScript SDK is now Apache-2.0; Cloudflare's Agents SDK deprecated its stateful MCP class.
- Recommended shape for this project: put the agent loop in TypeScript on the client or edge using the AI SDK (provider-neutral, client tools, typed parts that map one-to-one onto the app's typed UI commands), and keep Python for offline data building and evaluation. If a server-side loop in Python is preferred, Pydantic AI with its Vercel-AI or AG-UI stream adapter preserves the same front end.
- The Claude Agent SDK is the wrong tool for a $0 browser/edge product (subprocess per session, about 1 GiB each, commercial terms, no browser runtime); it remains useful for the developer's own coding workflow and for evaluation harnesses.
- A whole-loop-in-browser design is feasible: AI SDK core plus a provider client configured with the user's key, with tools executing locally against an in-browser dataset and `DirectChatTransport` or a custom transport replacing the HTTP hop. This is off the documented happy path (the transport docs do not mention browsers), so budget time for it.
- Security implications of BYOK in the browser: the key is only as safe as the page's defence against script injection. Practical mitigations: strict Content-Security-Policy, no third-party scripts, never send the key to the app's own server, keep it in memory by default with explicit opt-in persistence, encourage spend-capped and expiring keys (OpenRouter's PKCE flow gives this for free), and treat all fetched literature or database text as untrusted input to the model. OpenRouter's own storage advice conflicts with a pure static app, so the notes above should be presented as a conscious trade-off, not as best practice.
- Provider coverage for BYOK: Anthropic and OpenAI work directly; OpenRouter is the cleanest UX and gives access to cheap or free models; Gemini direct-from-browser contradicts Google's guidance and is best reached through OpenRouter or a thin proxy.
- A thin optional proxy on the Workers free plan (rate-limited, no key storage) is a reasonable fallback for users without keys, but it is the one component that can generate cost.

### Gaps
- Current version numbers for Pydantic AI, LangGraph, Mastra, the OpenAI Agents SDK, CopilotKit and assistant-ui were not shown on the pages fetched.
- Whether `DirectChatTransport` is supported in browsers, and whether the AI SDK's Anthropic provider sets the browser-access header itself, were not confirmed.
- CORS behaviour of the OpenAI, OpenRouter and Gemini HTTP endpoints was not tested first-hand; OpenAI's and OpenRouter's browser support is inferred from their SDK and docs.
- Google ADK, Microsoft Agent Framework and LlamaIndex were not researched beyond their appearance in the AG-UI integration list.

## 5. Agent-driven and generative UI: protocols, patterns and concrete examples

### Takeaway
Three complementary approaches have stabilised: the agent calls typed front-end tools and shares state with the app (AG-UI 1.0, AI SDK client tools, CopilotKit hooks), the agent emits a declarative component description rendered from an app-owned catalogue (A2UI 1.0, json-render), or the agent's server ships a sandboxed mini-app (MCP Apps). Well-engineered canvas, map and 3D integrations (tldraw's agent kit, OpenAssistant for Kepler.gl, Blender MCP, PyMOL copilots) all use the first approach with a small validated action vocabulary plus a compact, structured snapshot of view state fed back to the model.

### Cited Findings

#### Protocols and libraries
- AG-UI: an open, event-based agent-to-front-end protocol that originated at CopilotKit with LangChain and CrewAI; positions itself beside MCP (agent to tools) and A2A (agent to agent); building blocks are streaming chat, shared state, front-end tool calls, human-in-the-loop interrupts, generative UI and custom events. Version 1.0 is out and backward compatible; MIT; about 21.7k stars; SDKs for TypeScript (`@ag-ui/client`, `@ag-ui/core`), Python (`ag-ui-protocol`), .NET and others; transports are HTTP with server-sent events or a binary protobuf option; 31 event types in eight families. — [AG-UI introduction](https://docs.ag-ui.com/introduction); [ag-ui repository](https://github.com/ag-ui-protocol/ag-ui)
- AG-UI event model: lifecycle (`RunStarted`, `RunFinished`, `RunError`, steps), text messages, tool calls (`ToolCallStart`, `ToolCallArgs` streamed fragments, `ToolCallEnd`, `ToolCallResult`), state (`StateSnapshot` replaces the whole state; `StateDelta` carries RFC 6902 JSON Patch operations; `MessagesSnapshot` for recovery), activity, reasoning, sub-agents, and `Raw`/`Custom` passthrough; human input is modelled as a run finishing with an interrupt outcome and a new run resuming with the answer. — [AG-UI events](https://docs.ag-ui.com/concepts/events)
- A2UI: an open-source generative-UI format now at v1.0 (Apache-2.0); agents send declarative JSON with two-way data bindings and never executable code; the client owns a locked component catalogue; renderers exist for React, Lit, Angular, Flutter, SwiftUI and Jetpack Compose; A2UI surfaces can run inside an MCP App and vice versa. — [a2ui.org](https://a2ui.org/)
- CopilotKit: MIT; 39.0k stars; self-hosted runtime (cloud optional); supports AG-UI 1.0 and A2UI 1.0; frames three kinds of generative UI — controlled (agent picks registered components via tool calls and state), declarative (A2UI), and open-ended (sandboxed MCP Apps). Hooks: `useFrontendTool` (client-side tool with schema and handler), `useComponent`, `useHumanInTheLoop` (pause a tool call for approval, edit or input), `useInterrupt`, `useRenderTool`, `useDefaultRenderTool`, `useRenderToolCall`, and `useAgent` for programmatic access. — [CopilotKit repository](https://github.com/CopilotKit/CopilotKit); [CopilotKit hook guide](https://docs.copilotkit.ai/concepts/which-hook)
- assistant-ui: MIT; 13.4k stars; composable React chat primitives with runtime adapters for the AI SDK, LangGraph, AG-UI, A2A, Google ADK and custom back ends; tool calls can render as React components, with inline approvals and front-end actions exposed to the model; optional paid cloud for thread persistence. — [assistant-ui repository](https://github.com/assistant-ui/assistant-ui)
- AI SDK generative UI: tool results arrive as typed message parts and the client switches on tool name and state to render a component (loading on input, component on output, error text on failure). — [AI SDK: generative user interfaces](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)
- json-render (Vercel Labs): Apache-2.0; about 19.8k stars; the developer defines a component catalogue with Zod prop schemas and allowed actions, the model emits a JSON spec, the catalogue generates the system prompt, specs render progressively while streaming, and props can bind to state; renderers include React, Vue, Svelte, Solid, React Native and React Three Fiber, and an MCP Apps package exists; parts are labelled experimental. — [json-render repository](https://github.com/vercel-labs/json-render)
- Google's generative-UI research (18 November 2025): models generate a whole custom interactive interface per prompt (shipped as experiments in the Gemini app and AI Mode); raters preferred these outputs to standard text/markdown when speed was ignored, with expert-made sites still best; generation can take a minute or more and outputs sometimes contain inaccuracies. — [Google Research blog](https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/)

#### Concrete agent-controlled visual applications
- tldraw agent starter kit (canvas): the agent receives both screenshots and structured shape data (simplified shapes in view, clustered counts outside it, plus the user's selection, viewport and recent actions); each capability is a typed action with a schema; actions are sanitised before being applied or saved (helpers repair common model mistakes such as non-existent shape IDs) and applied only once streaming of that action completes; "modes" restrict which context and actions are available; the chat panel shows the agent's actions in its history. — [tldraw agent starter kit](https://tldraw.dev/starter-kits/agent)
- OpenAssistant (maps and spatial analysis, used with Kepler.gl): tools are defined with a Zod parameter schema, an `execute` function and an app-supplied `context` (for example a function returning the current dataset); each result is split into a compact part for the model and a separate payload for rendering; an `onToolCompleted` callback lets the app update visuals; ships components for Kepler.gl, Leaflet, ECharts and Vega-Lite and in-browser DuckDB; built on the Vercel AI SDK; MIT. — [OpenAssistant repository](https://github.com/GeoDaCenter/openassistant)
- Blender MCP (3D): a Blender add-on runs a socket server and an MCP server sends JSON commands with a type and parameters; tools return a compact scene summary and viewport renders, and creation/modification goes through arbitrary Python execution; about 35.8k stars; the README warns about arbitrary code execution and an unauthenticated socket. — [blender-mcp](https://github.com/ahujasid/blender-mcp)
- ChatMol (molecular viewer): began as a PyMOL plugin; version 2 runs a tool-calling loop that turns natural language into PyMOL commands and can inspect the session and review rendered output; MIT; 376 stars. — [ChatMol repository](https://github.com/ChatMol/ChatMol)
- MolViewSpec (Mol*): a JSON format (MIT) describing a molecular view as a declarative tree (download, parse, structure, component selection, representation and so on) with a Python builder (`molviewspec`) and a TypeScript package; Mol* is the reference implementation; the Mol* organisation also maintains "mol-view-stories". No MCP or agent repository was visible among the organisation's listed repositories. — [mol-view-spec repository](https://github.com/molstar/mol-view-spec); [molstar on GitHub](https://github.com/molstar)
- MCP Apps examples include a CesiumJS globe and Three.js scenes, and Claude's app-tools mechanism lets the host model call tools registered by a live view to change what it shows. — [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview); [Claude docs: app tools](https://claude.com/docs/connectors/building/mcp-apps/app-tools.md)
- Cloudflare's Agents SDK syncs agent state changes to all connected clients automatically, an infrastructure-level version of shared state. — [cloudflare/agents](https://github.com/cloudflare/agents)

#### Agent-controlled interfaces versus chat sidebars
- Amelia Wattenberger's essay argues chat is a poor default: it shows no affordances for what the system can do, pushes prompt-writing work onto the user, isolates responses so they are hard to compare or refine, and forces constant switching between doing and evaluating; she favours tools that support judgment through direct manipulation ("Good tools make it clear how they should be used."). — [Wattenberger: Why chatbots are not the future](https://wattenberger.com/thoughts/boo-chatbots)

### Inferences
- The app's existing design (typed UI commands streamed before prose) is exactly the "front-end tool call plus shared state" pattern that AG-UI, the AI SDK and CopilotKit have since standardised. The 2.0 version should keep its own small command vocabulary and express it as client-executed tools, so the same commands can be driven by the in-app agent, by tests, and (through MCP App "app tools") by external hosts.
- Practices to lift directly: validate and repair every command before applying it (tldraw); give the model a compact structured snapshot of view state every turn — selection, filters, camera target, loaded structure, graph root — rather than screenshots alone (tldraw, AG-UI `StateSnapshot`); return a small model-facing result and keep the heavy payload for the renderer (OpenAssistant); apply a command only when its arguments are complete; show every agent action in the transcript as a reversible step.
- Undo and human-in-the-loop: make every command an entry on the same undo stack as user actions and reserve explicit approval for costly or irreversible operations (bulk external API calls, exports, anything that spends the user's key heavily). AI SDK `toolApproval` and CopilotKit `useHumanInTheLoop` implement the approval half; the undo half is application logic.
- For the structure viewer, have the agent emit MolViewSpec (declarative, schema-checkable, diffable, serialisable into a shareable link) rather than imperative viewer calls; it gives grounding and reproducibility for free and matches how the canvas and map examples constrain the model.
- Reserve generative UI for ad-hoc result cards and small charts via a constrained catalogue (json-render or A2UI). Do not generate whole interfaces for core scientific views: Google's own evaluation notes minute-scale latency and inaccuracies, and correctness of scientific visuals matters more than novelty.
- A library choice that minimises lock-in: AI SDK UI primitives or assistant-ui for the transcript, own state store for the visual surfaces, AG-UI-compatible events only if a Python agent back end is kept.

### Gaps
- No Mol*-specific agent or MCP integration was verified (only 10 of the Mol* organisation's 23 repositories were visible, and web search was unavailable by then); PyMOL-oriented copilots were the closest molecular examples found.
- Kepler.gl's own AI-assistant documentation, and engineering write-ups from mapping vendors (Felt, CARTO, Foursquare) or from Mol*/RCSB/PDBe teams, were not retrieved.
- The tldraw kit's page does not document undo or accept/reject review of agent changes, and its licence terms were not shown.

## 6. Grounding and hallucination control for biomedical question answering

### Takeaway
Published numbers consistently show that letting a model answer biomedical questions from memory, or even from retrieved text with self-written citations, leaves a large unsupported fraction, while structured tool access with execution closes most of the gap but still trails experts. The robust recipe is deterministic entity resolution, typed queries over structured data, machine-checkable citations to records, and a separate verification pass — which is the existing "grounded first, narrate second, fall back wholesale" design generalised to multi-step tool use.

### Cited Findings
- Text-to-SQL in biomedicine: BiomedSQL has 68,000 question/SQL/answer triples over a harmonised BigQuery knowledge base (gene–disease associations, omics-based causal inference, drug approvals) that require implicit domain reasoning such as significance thresholds; the best model under baseline prompting (Gemini 3 Pro) reaches 58.1% execution accuracy, a custom multi-step agent 62.6%, and domain experts 90.0% (paper last revised August 2026). — [BiomedSQL on arXiv](https://arxiv.org/abs/2505.20321)
- General text-to-SQL: on BIRD (12,751 question–SQL pairs, 95 databases) human execution accuracy is 92.96% and the best system on the main test leaderboard is 83.40% (October 2026); the interactive variant's best reported success rate was 16.33%. — [BIRD benchmark](https://bird-bench.github.io/)
- Enterprise text-to-SQL: Spider 2.0 has 632 workflow problems over databases often exceeding 1,000 columns; o1-preview solved 17.1% in the original paper, and current leaderboard leaders are agent systems scoring 96.70 (Snow), 76.23 (Lite) and 65.6 (DBT). — [Spider 2.0](https://spider2-sql.github.io/)
- Text-to-Cypher: CypherBench provides 11 large property graphs (7.8 million entities, more than 10,000 questions) and argues that property-graph views are far easier for LLMs to query than raw RDF schemas. — [CypherBench on arXiv](https://arxiv.org/abs/2412.18702)
- GraphRAG criticisms: one comprehensive analysis starts from the observation that GraphRAG often does worse than plain RAG on many real-world tasks and introduces a benchmark to identify when graphs help (complex reasoning and contextual summarisation rather than simple fact retrieval); a systematic comparison finds RAG and GraphRAG have distinct strengths by task and that combining them gives consistent gains. — [When to use Graphs in RAG](https://arxiv.org/abs/2506.05690); [RAG vs. GraphRAG](https://arxiv.org/abs/2502.11371)
- Citation faithfulness in medicine: SourceCheckup (1,200 questions, more than 40,000 statement–source pairs, five models) found 50–90% of LLM responses were not fully supported by the sources they cited; even GPT-4 with retrieval had about 30% of individual statements unsupported and nearly half of responses not fully supported; the automated checker agreed with physicians 88% of the time. — [SourceCheckup on arXiv](https://arxiv.org/abs/2402.02008)
- API calls beat retrieval for genomics facts: GeneGPT, which teaches a model to call NCBI web APIs, averaged 0.83 on GeneTuring against 0.44 for retrieval-augmented Bing and 0.12 for ChatGPT; API demonstrations worked better than API documentation in context. — [GeneGPT on arXiv](https://arxiv.org/abs/2304.09667)
- Database questions without tools are close to hopeless even for 2026 models (0.058 on LABBench2 database QA for GPT-5.2 in the bare setting), while literature QA with tools reaches about 0.80. — [Inspect Evals: LAB-Bench 2](https://ukgovernmentbeis.github.io/inspect_evals/evals/lab_bench_2/index.html)
- Generic one-endpoint-per-tool wrappers over a biomedical GraphQL API produce wasteful, error-prone workflows on aggregation and multi-entity questions. — [Open Targets blog](https://blog.opentargets.org/official-open-targets-mcp/)
- Verification passes: Chain-of-Verification drafts an answer, plans verification questions, answers them independently of the draft, then writes a verified answer, and reduces hallucinations on list questions, closed-book QA and long-form generation. Production systems use the same idea: Kosmos links every statement to code or literature, and Claude Science's reviewer checks claims against the execution record without re-running analyses. — [Chain-of-Verification on arXiv](https://arxiv.org/abs/2309.11495); [Kosmos on arXiv](https://arxiv.org/abs/2511.02824); [Claude Science overview](https://claude.com/docs/claude-science/overview)
- Even expert-validated agent output is imperfect: PaperQA2's detected contradictions were validated 70% of the time, and Kosmos statements 79.4%. — [PaperQA2 on arXiv](https://arxiv.org/abs/2409.13740); [Kosmos on arXiv](https://arxiv.org/abs/2511.02824)
- Anthropic Citations (stable, all active models): documents are chunked (sentences for plain text and PDF; your own blocks for "custom content" documents) and responses carry citations with exact locations; because the API extracts the cited text itself, citations are guaranteed to point into the supplied documents; cited text is not billed as output tokens; Anthropic reports the feature cites the most relevant passages more reliably than prompt-only approaches; it cannot be combined with structured outputs (400 error), and the API does not guarantee that every field or claim gets a citation. — [Claude docs: Citations](https://platform.claude.com/docs/en/build-with-claude/citations)
- Search-result content blocks (stable) let a custom tool return records with a `source` (any stable string, including an internal identifier) and `title`, and Claude then cites them the way it cites web results, either from tool results or as top-level user content. — [Claude docs: Search results](https://platform.claude.com/docs/en/build-with-claude/search-results)
- Structured outputs (GA): constrained decoding guarantees schema-valid JSON for responses and, with `strict: true`, for tool inputs; unsupported schema features include recursion, numeric and string-length constraints and `additionalProperties` other than false; compiled grammars are cached for 24 hours. — [Claude docs: Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

### Inferences
- Architecture that follows from the evidence: (1) a deterministic resolver tool maps names to stable identifiers (the project's whole-term matching rule is the right instinct; models must never supply accessions from memory); (2) a small set of typed, parameterised query tools covers the common intents over the local dataset; (3) a read-only SQL tool over the same store is offered for long-tail questions, with schema subsets, row limits and returned row IDs — accepting that free text-to-SQL tops out around 60–85% on public benchmarks, so its results need to be shown, not just narrated; (4) every tool result carries record identifiers and source URLs; (5) prose is generated last and must cite those identifiers.
- Do not build GraphRAG. The app already has a curated typed graph; graph questions should be answered by deterministic traversals (neighbours, paths, shared targets) exposed as tools. LLM-extracted graphs over text add cost and, per the 2025–26 evaluations, frequently lose to plain retrieval on fact lookups.
- Citations versus structured outputs is a forced choice on Claude; a two-pass design sidesteps it: pass one produces a structured, schema-valid "facts used" object (IDs, values, sources) from tool results, pass two narrates with citation markers. Provider-neutral fallback: require inline `[record-id]` markers and verify in code that each marker exists in this turn's tool results and that numbers and identifiers in the prose appear in the cited record.
- The existing all-or-nothing fallback generalises well: if verification fails (unknown ID, unsupported number, missing citation), discard the narration and show the structured answer. This turns the roughly 20–30% unsupported-statement rates seen in the literature into a measurable, bounded "fallback rate".
- Literature answers deserve stricter treatment than database answers: quote-level citations to abstracts via search-result blocks, and an explicit "evidence not found" outcome.
- Custom-content citation blocks map naturally onto database rows: one block per record makes each record the minimum citable unit.

### Gaps
- No headline accuracy figures for text-to-Cypher were in the CypherBench abstract, and none were found for biomedical knowledge-graph question answering.
- Published rates at which models invent gene, protein or variant identifiers (for example the GeneTuring results) and entity-normalisation benchmarks were not retrieved.
- No independent accuracy figures for Anthropic's Citations feature were found (only the vendor's qualitative claim); OpenAI's and Google's citation and grounding features were not researched.
- Current BioASQ system results were not retrieved.

## 7. Advanced tool-use features from model providers and how they change agent design and cost

### Takeaway
By late 2026 on-demand tool discovery, code-driven tool orchestration, prompt caching, batch processing, citations, structured outputs and portable "skills" are stable, documented features on Anthropic's platform, with OpenAI offering a comparable tool-search mechanism. They push agent design toward a small always-loaded tool core, a searchable long tail, intermediate data kept out of the model's context, and a byte-stable prompt prefix.

### Cited Findings
- Tool search (Anthropic; stable, all current models): mark tools `defer_loading: true` and add a regex or BM25 search tool; only the search tool and non-deferred tools enter context, and matches are expanded on demand (5 by default). Anthropic's figures: a five-server setup can spend about 55k tokens on definitions before any work, tool search typically cuts that by more than 85%, and tool-selection accuracy degrades beyond 30–50 loaded tools. Limits and guidance: up to 10,000 deferred tools; keep the 3–5 most-used tools loaded; use it from roughly 10 tools or 10k tokens of definitions; discovered definitions are appended so the cached prefix survives; it is not billed as a separate tool; you can implement your own search (for example embeddings) by returning `tool_reference` blocks. — [Claude docs: Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- Anthropic's launch post (24 November 2025) reported: 58 tools from five servers costing about 55K tokens; startup overhead cut from about 77K to 8.7K tokens; accuracy on MCP evaluations rising from 49% to 74% (Opus 4) and 79.5% to 88.1% (Opus 4.5) with tool search; programmatic tool calling cutting average tokens from 43,588 to 27,297 on complex research tasks; and tool-use examples lifting complex-parameter accuracy from 72% to 90%. — [Anthropic engineering: Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- Programmatic tool calling (Anthropic; stable): Claude writes code in the hosted code-execution container that calls your tools (enabled per tool with `allowed_callers`); tool results go to the running code rather than the model's context, and only the script's final output is counted; Anthropic cites about 38% fewer billed input tokens on a 75-tool benchmark with unchanged accuracy and typical savings of 20–40% for requests with 10–49 tools. Constraints: not compatible with strict tools, forced tool choice, or MCP-connector tools; a pending call times out after about four minutes; data is retained up to 30 days (not eligible for zero data retention); it is billed as code execution; it is least useful for strictly sequential workflows where the model must reason over each result. — [Claude docs: Programmatic tool calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)
- "Code execution with MCP" (Anthropic, 4 November 2025): presenting MCP servers as code APIs that the agent explores and calls from a sandbox cut one example from about 150,000 tokens to 2,000 (98.7%), at the price of needing a secure sandbox, resource limits and monitoring. — [Anthropic engineering: Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Cloudflare "Code Mode" (26 September 2025): convert MCP tools into a TypeScript API and have the model write code against it inside an isolate with no general internet access and no API keys in the generated code; rationale is that models have seen far more real code than tool-call examples and that chaining avoids round trips. — [Cloudflare blog: Code Mode](https://blog.cloudflare.com/code-mode/)
- Prompt caching (Anthropic): cache writes cost 1.25× base input for the 5-minute default lifetime and 2× for one hour; reads cost 0.1× (lower on the newest models); minimum cacheable prefix is 512–4,096 tokens depending on model; up to four explicit breakpoints, or one automatic top-level setting; changing tool definitions invalidates everything, and toggling web search, citations or speed invalidates system and messages; cache hits do not count against rate limits; caches are isolated per organisation and workspace. — [Claude docs: Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- The MCP 2026-07-28 spec now asks servers to return tool lists in deterministic order specifically to improve client caching and LLM prompt-cache hit rates. — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Message Batches (Anthropic): asynchronous processing at 50% lower cost, most batches finishing within an hour; explicitly suggested for large-scale evaluations. — [Claude docs: Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)
- Agent Skills: an open format originated by Anthropic — a folder with a `SKILL.md` (name, description, instructions) plus optional scripts and references — loaded by progressive disclosure (names and descriptions at start-up, full instructions on activation, bundled files on demand) and adopted across agent products; MCP has a Beta "Skills over MCP" extension, and OpenAI's plugin model bundles skills with MCP servers. — [agentskills.io](https://agentskills.io/); [MCP extensions overview](https://modelcontextprotocol.io/extensions/overview); [OpenAI Apps SDK docs](https://developers.openai.com/apps-sdk/)
- OpenAI tool search (Responses API, `gpt-5.4` and later): add a `tool_search` tool and mark functions or MCP servers `defer_loading: true`; functions are best grouped into namespaces of fewer than ten; hosted and client-executed modes exist; loaded tools are injected at the end of the context to preserve the cache. — [OpenAI: tool search guide](https://developers.openai.com/api/docs/guides/tools-tool-search)
- These features are reachable through provider-neutral SDKs: the AI SDK's Anthropic provider documents tool search, programmatic tool calling, cache control, citations and context management. — [AI SDK Anthropic provider](https://ai-sdk.dev/providers/ai-sdk-providers/anthropic)

### Inferences
- Tool-surface design for this app: always-loaded core of roughly five to eight tools (resolve entity, query dataset, graph traversal, UI commands, literature search), with external-API tools (Open Targets, ChEMBL, Europe PMC, Ensembl and so on) deferred behind search. A client-side search over the app's own tool registry works with any provider and is trivial to build; provider-native tool search is an optimisation.
- The biggest cost lever for multi-step questions is keeping bulk data out of the context. Hosted programmatic tool calling does this but runs in the provider's container, costs extra and is provider-specific. The in-browser equivalent — one `run_query` tool executing SQL against a local analytical engine and returning only aggregates and IDs — delivers most of the benefit at zero server cost and fits the BYOK model.
- Cache discipline matters for BYOK users' bills: freeze the system prompt and tool list (sorted, no timestamps), put volatile UI state at the end of the conversation rather than in the system prompt, and avoid adding or removing tools mid-session (use deferred loading instead).
- Batch processing halves the cost of offline work: evaluation runs and any precomputed summaries or embeddings for the proteome-scale dataset.
- Packaging domain know-how ("how to assess a target", "how to read pLDDT") as skills keeps the base prompt small and makes the same guidance reusable by external hosts through the MCP server.
- Provider neutrality has a price: tool search, programmatic calling, citations and caching controls all differ by provider, so treat them as optional accelerators behind the app's own abstractions (own tool registry, own citation markers, own verification).

## 8. Evaluation: benchmarks for biology agents and a small, credible custom harness

### Takeaway
Public biology-agent benchmarks are useful mainly as calibration and as sources of task design ideas; several are saturated, noisy, or far too expensive and broad for a portfolio app to claim results on. A credible harness for this project is a few dozen to a couple of hundred tasks derived from its own structured data, graded mostly by code against ground truth, with a small human-calibrated judge for narrative quality, run with uncertainty estimates and gated in CI.

### Cited Findings

#### Benchmarks
- LAB-Bench (FutureHouse, 2024): 2,457 multiple-choice questions in eight categories (LitQA2, DbQA, SuppQA, SeqQA, FigQA, TableQA, ProtocolQA, Cloning Scenarios); 80% public and 20% held out to monitor contamination; nearly all models then underperformed human experts and most were near chance on figure questions. — [FutureHouse: LAB-Bench](https://www.futurehouse.org/research/lab-bench-measuring-capabilities-of-language-models-for-biology-research); [LAB-Bench on arXiv](https://arxiv.org/abs/2407.10362)
- LABBench2 (2026; arXiv 2604.09554): life-science tasks spanning literature, databases, figures, tables, protocols, sequences, cloning, patents and clinical trials; configurable file delivery (file, inject, retrieve) and solver modes (bare, server-side tools, sandboxed agent); graded by an LLM judge or deterministic validators depending on subset; published GPT-5.2 scores range from 0.058 to 0.799 by subset. — [Inspect Evals: LAB-Bench 2](https://ukgovernmentbeis.github.io/inspect_evals/evals/lab_bench_2/index.html)
- BixBench: version 1.5 has 205 questions from 60 analysis "capsules" (published notebooks plus data); open-ended answers are graded by an LLM grader, multiple-choice by exact match with an optional refusal choice; Apache-2.0; agents run in a Docker notebook environment. — [BixBench repository](https://github.com/Future-House/BixBench)
- BioML-bench: end-to-end biomedical ML tasks across four domains; agents on average underperform human baselines. — [BioML-bench preprint](https://www.biorxiv.org/content/10.1101/2025.09.01.673319v1)
- ScienceAgentBench: 102 tasks from 44 papers in four disciplines, each producing a self-contained Python program; validated by nine experts; reports execution results and cost. — [ScienceAgentBench on arXiv](https://arxiv.org/abs/2410.05080)
- BioASQ: the fourteenth challenge ran in 2026 with biomedical semantic QA (retrieval, exact answers, summaries), a "Synergy" task on developing topics, clinical summarisation, relation extraction, ICD-10 coding and gut–brain information extraction. — [BioASQ](https://www.bioasq.org/)
- PubMedQA: 1k expert-labelled yes/no/maybe questions (plus 61.2k unlabelled and 211.3k generated); human performance 78.0% accuracy; the leaderboard's top entry is still GPT-4 with Medprompt at 82.0% from November 2023, so the benchmark is effectively saturated and stale. — [PubMedQA](https://pubmedqa.github.io/)
- ProteinLMBench: 944 manually verified multiple-choice questions on protein understanding. — [ProteinLMBench on arXiv](https://arxiv.org/abs/2406.05540)
- Others encountered: Biomni-Eval1 (433 items, 10 tasks); scBench (30 single-cell analysis tasks with deterministic grading); BiomedSQL (68,000 text-to-SQL triples); TxAgent's five drug-reasoning benchmarks; and the Inspect Evals collection lists 201 evaluations including LAB-Bench, LABBench2, BixBench, scBench, PubMedQA, MedQA, HealthBench, ChemBench, SciCode, PaperBench, CORE-Bench and the hazardous-knowledge sets WMDP and SOS-Bench. — [Biomni repository](https://github.com/snap-stanford/Biomni); [Inspect Evals index](https://ukgovernmentbeis.github.io/inspect_evals/); [BiomedSQL on arXiv](https://arxiv.org/abs/2505.20321)
- Benchmark label quality is itself a risk: FutureHouse reported that a large share of chemistry and biology answers in Humanity's Last Exam are likely wrong. — [FutureHouse research index](https://www.futurehouse.org/research-announcements)

#### Harness tools
- Inspect (UK AI Security Institute with Meridian Labs): open-source Python framework built around Task = Dataset + Solver + Scorer; built-in scorers include substring matching and model-graded QA; a built-in ReAct agent; custom, MCP and standard tools; Docker, Kubernetes and Modal sandboxes; a web log viewer and VS Code extension; more than 20 model providers plus local inference. — [Inspect](https://inspect.aisi.org.uk/)
- promptfoo: MIT, about 27.7k stars; CLI and library for evaluation and red-teaming with declarative configs and CI/CD integration; evaluations run locally; the README states it is now part of OpenAI and remains open source. — [promptfoo repository](https://github.com/promptfoo/promptfoo)
- Langfuse: MIT except `ee` folders, about 37.8k stars; part of ClickHouse since January 2026; OpenTelemetry-based tracing, prompt management, datasets and experiments, LLM-as-judge and code evaluators, manual labelling; self-hostable, with a free cloud tier. — [Langfuse repository](https://github.com/langfuse/langfuse)
- DeepEval: Apache-2.0, about 19.7k stars; pytest-style framework with G-Eval, DAG, faithfulness, hallucination, tool-correctness and task-completion metrics, trace-level agent evaluation and synthetic data generation; the Confident AI cloud is separate and optional. — [DeepEval repository](https://github.com/confident-ai/deepeval)
- Framework-native options: Pydantic Evals grades final outputs and tool-call trajectories; Mastra ships built-in evals. — [Pydantic AI overview](https://pydantic.dev/docs/ai/overview/); [Mastra repository](https://github.com/mastra-ai/mastra)

#### Method
- Anthropic's agent-evals guide (9 January 2026): distinguish tasks, trials, graders, transcripts and outcomes; combine code-based graders (fast, objective, brittle), model-based graders (flexible, need calibration) and human review (gold standard, slow); separate capability evals (start low) from regression evals (should stay near 100%); choose pass@k or pass^k according to whether one success or consistency matters; grade outcomes rather than exact tool paths; give partial credit; isolate trials; keep reference solutions; balance should and should-not cases; read transcripts; start with 20–50 tasks drawn from real failures. For research-style agents it recommends combining groundedness, coverage and source-quality checks; for judges, calibrate against experts, allow an "unknown" verdict and use one judge per dimension. — [Anthropic engineering: Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Statistics (Anthropic, November 2024): report the standard error and a 95% confidence interval; cluster standard errors when questions share context (naive errors were more than three times too small in practice); resample to reduce within-question variance; compare systems with paired differences on the same questions; use power analysis to size the eval. — [Anthropic: A statistical approach to model evals](https://www.anthropic.com/research/statistical-approach-to-model-evals)
- LLM-as-judge pitfalls and remedy (Hamel Husain; updated September 2026): have one domain expert give binary pass/fail judgments with written critiques, build the judge prompt from those critiques, validate on held-out labels using true-positive and true-negative rates rather than raw agreement, and avoid many metrics, uncalibrated 1–5 scales and generic off-the-shelf metrics. — [Hamel Husain: LLM-as-a-judge guide](https://hamel.dev/blog/posts/llm-judge/)
- Anthropic's general guidance ranks grading methods by scalability (code, then LLM, then human), prefers many automatically graded cases over a few hand-graded ones, and advises detailed rubrics, discrete outputs, reasoning-before-verdict and a different model for grading than for generation. — [Claude docs: Develop tests](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)
- Batch APIs are suggested for large evaluation runs at half cost. — [Claude docs: Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

### Inferences
- Dataset design for this app (ground truth computed from its own data, so grading is mostly deterministic): (a) entity-resolution cases including adversarial ones (ordinary words that collide with gene symbols, ambiguous names, unknown entities that must be rejected); (b) single-hop lookups with exact answers; (c) multi-hop graph and aggregation questions whose answers are computed by reference code; (d) UI-control tasks graded on final interface state (filters, loaded structure, graph root, camera target), not on the path; (e) literature questions graded on citation validity and whether the cited passage contains the claim; (f) should-refuse and out-of-scope prompts (clinical advice, hazardous requests, questions the data cannot answer); (g) prompt-injection cases embedded in fetched text.
- Grading stack: exact or set match and numeric tolerance for (a)–(c); state diff for (d); deterministic checks that every cited ID exists in the turn's tool results and that numbers in the prose appear in cited records for (e); a small LLM judge for narrative clarity only, calibrated on roughly 50 expert-labelled examples and reported with its true-positive and true-negative rates.
- Metrics a portfolio project can honestly report: task success with n and 95% confidence interval; consistency (all-of-k trials) on a subset; grounded-claim rate and unsupported-claim rate; fallback rate (how often narration was discarded for the structured answer); tool-call error rate and mean steps; cost and latency per task; refusal correctness on the safety set. State the model, date, scaffold version and number of trials.
- What not to claim: leaderboard-style results on LAB-Bench, BixBench or similar unless the full protocol is followed; "accuracy" from an uncalibrated judge; productivity or discovery claims. If a public benchmark is used at all, a clearly labelled subset (for example the database-QA and sequence-QA portions of LABBench2, where tools matter most) is the informative choice.
- CI gating: run the deterministic subset on every pull request against recorded tool outputs and a cheap model (or replayed model outputs for pure plumbing checks), fail on any regression in the regression suite, and run the full suite nightly or manually using batch pricing; compare runs with paired differences rather than raw percentages because the suite is small.
- Tool choice: Inspect is the most natural fit (Python backend, agent and MCP support, the biology benchmarks already implemented, strong logs); promptfoo is the lightest option for prompt-level regression tests in CI but is now owned by a model vendor; Langfuse adds tracing and datasets if observability is wanted. One harness plus the framework's own test runner is enough.

## 9. Safety: biosecurity and dual use, protein-design features, and medical disclaimers

### Takeaway
Model providers now enforce biology-specific safeguards at the API layer that are deliberately broad, so a public biology app must expect and handle false-positive refusals on legitimate questions; relaxed access exists only for verified organisations. Responsible open tools combine scope limits (what data and capabilities are offered), training-data or capability exclusions for pathogens, screening commitments for anything that leads to synthesis, and explicit research-only and not-for-clinical-use positioning.

### Cited Findings
- Anthropic API behaviour: current Claude models include safety classifiers that return a normal response with `stop_reason: "refusal"` and a category; the `bio` category covers requests that could enable biological harm and the documentation states that beneficial life-sciences work can also trigger it; a `bio` refusal that arrives before any output is still billed; a server-side fallback option can retry a refused request on another model. — [Claude docs: Refusals and fallback](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback)
- Anthropic's own science product says some safeguards are intentionally broad and can flag legitimate biology work; it pauses the session, can automatically retry on another model, and offers a "Life Sciences Verification Program" (beta) under which verified organisations get fewer restrictions. — [Claude Science: Safeguards](https://claude.com/docs/claude-science/safeguards)
- The verification programme is for organisations on Enterprise, Team or API plans (not individuals or consumer plans), relaxes real-time biology classifiers while keeping protections against the most serious misuse, excludes the Claude Fable model family, has an optional higher-risk add-on for areas such as virology, takes about three business days to decide, and requires 30-day retention with monitoring. — [Anthropic support: Life Sciences Verification Program](https://support.claude.com/en/articles/16975617)
- Background: Anthropic activated its ASL-3 deployment protections on 22 May 2025 — real-time classifiers narrowly aimed at chemical, biological, radiological and nuclear weapons workflows, a bug bounty, and targeted exemptions for vetted users — and acknowledged occasional impact on legitimate queries. — [Anthropic: Activating ASL-3 protections](https://www.anthropic.com/news/activating-asl3-protections)
- OpenAI (18 June 2025): trains models to refuse harmful requests and give only high-level answers on dual-use topics, runs always-on detection with human review and enforcement, is building trusted access for vetted institutions, accepts that this limits helpful biology assistance for the general public, and commits not to release a high-biology-capability model without sufficient mitigations. — [OpenAI: Preparing for future AI capabilities in biology](https://openai.com/index/preparing-for-future-ai-capabilities-in-biology/)
- Usage policies: Anthropic's policy (effective 12 November 2026) prohibits helping design, synthesise, produce or acquire biological or chemical weapons, lists diagnosing a medical condition and healthcare triage among high-risk uses that require review by a qualified person and disclosure that AI was used, and requires consumer-facing chatbots to disclose that users are talking to AI. OpenAI's policy (effective 20 November 2026) prohibits tools that give tailored advice requiring a licence without appropriate involvement of a licensed professional, and weapons development including CBRNE. — [Anthropic usage policy](https://www.anthropic.com/legal/aup); [OpenAI usage policies](https://openai.com/policies/usage-policies/)
- Product positioning by leading tools: Claude Science is described as a research tool not intended for clinical or diagnostic use, with a warning to verify results; Google says Co-Scientist is not a replacement for scientific or clinical expertise, was subject to independent CBRN-misuse evaluations, and uses custom classifiers to flag unethical research goals; Anthropic says Claude is designed to add contextual disclaimers and direct users to healthcare professionals. — [Claude Science overview](https://claude.com/docs/claude-science/overview); [Google DeepMind: Co-Scientist](https://deepmind.google/blog/co-scientist-a-multi-agent-ai-partner-to-accelerate-research/); [Anthropic: healthcare and life sciences](https://www.anthropic.com/news/healthcare-life-sciences)
- Protein-design community norms: the Responsible AI × Biodesign statement (8 March 2024, 206 signatories) commits signatories to obtain DNA synthesis only from providers with biosecurity screening, to evaluate and mitigate safety and security risks of protein-design software before and after release, to improve screening and risk-evaluation methods, and to report concerning practices. — [responsiblebiodesign.ai](https://responsiblebiodesign.ai/)
- Capability exclusion in an open biological model: Evo 2 (Arc Institute, February 2025) left pathogens that infect humans and other complex organisms out of its base training data and its developers checked that it does not give useful answers on those pathogens, while releasing weights and code openly. — [Arc Institute: Evo 2](https://arcinstitute.org/news/evo2)
- Domain agents acknowledge the issue: the CRISPR-GPT paper discusses ethical and regulatory considerations for automated gene-editing design and calls for responsible, transparent use. — [CRISPR-GPT on arXiv](https://arxiv.org/abs/2404.18021)
- Conventional security risks sit beside biosecurity: Biomni executes model-written code with full system privileges and asks users to sandbox it; Blender MCP exposes arbitrary code execution over an unauthenticated socket. — [Biomni repository](https://github.com/snap-stanford/Biomni); [blender-mcp](https://github.com/ahujasid/blender-mcp)
- Data-source terms are part of responsible operation: some biology databases carry non-commercial or attribution terms, and KEGG forbids remote hosting of its data by third parties. — [Claude Science: connectors and skills](https://claude.com/docs/claude-science/connectors-and-skills.md); [BioContextAI knowledgebase-mcp](https://github.com/biocontext-ai/knowledgebase-mcp)

### Inferences
- Direct observation from this research session (no external source): the fetch tool's built-in summariser model refused three benign pages with a `bio` classifier reason — a non-profit's page about DNA-synthesis screening software, a bioRxiv abstract about AI-designed nanobodies against a coronavirus, and a news article about patching synthesis-screening software. That is a small but concrete confirmation that false positives occur on legitimate biosecurity and virology-adjacent content, including on small, cheap models.
- Design consequences for a public biology agent: (1) treat provider refusals as a first-class outcome — detect them, show a neutral explanation, and fall back to the grounded structured answer (the existing all-or-nothing fallback already provides the mechanism) or to a different model if the user's key allows; (2) include virology- and toxin-adjacent but benign questions (viral entry receptors, toxin targets, immune-evasion biology at textbook level) in the evaluation set to measure the false-refusal rate per provider; (3) because users bring their own keys, state plainly that the provider's usage policy applies to their requests.
- Scope limits that keep the project clearly on the safe side: human proteins and public reference data only; read-only tools; no pathogen genomes, no enhancement- or transmissibility-related content, no synthesis or wet-lab protocols; no tool that executes arbitrary code on a server.
- Protein-design features are the main dual-use decision for 2.0. Options in increasing risk: structure and variant-effect visualisation only (low); pointing users to external design tools (low); in-app sequence generation or binder design (meaningful — would need pathogen/toxin target exclusions, clear research-only framing, no synthesis ordering hand-off, and alignment with the biodesign commitments). For a solo portfolio project the first two are the defensible choices.
- Medical disclaimers: position the app as research and education only, not for clinical or diagnostic use; disclose AI involvement in every session; never frame output as diagnosis or individual treatment advice (both providers' policies treat that as high-risk or restricted); when showing disease or variant associations, link to the underlying source and its evidence level rather than paraphrasing clinical significance; add a system-level rule to decline personal medical interpretation and point to professionals.
- For the MCP server exposed to other agent hosts: keep it read-only, mark tools as read-only in their annotations, rate-limit, attribute sources and licences in results, and treat any text returned from literature or third-party APIs as untrusted (prompt-injection risk for the calling host).
