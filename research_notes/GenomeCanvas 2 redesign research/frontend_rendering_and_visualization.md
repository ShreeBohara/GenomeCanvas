> Scope and method note (not a finding). State as of 2026-11-25. The shared web-search quota for this research run was exhausted after roughly 55 searches, so everything after that point was verified by fetching primary sources directly (official docs, changelogs, GitHub release pages, browser release notes) and by exact-name lookups against package registries (npm registry, jsDelivr metadata and CDN response headers, crates.io, Hugging Face Hub). ## 1. WebGPU in late 2026: support, default-enabled status, coverage and fallback

### Takeaway
WebGPU is on by default in Chrome/Edge on Windows, macOS, ChromeOS and Android 12+, in Safari 26 on every Apple platform, and in Firefox on Windows and Apple-Silicon macOS, but it is still missing or partial on Linux (Chrome only for Intel Gen12+ and NVIDIA-on-Wayland; Firefox not shipped), Firefox for Android, Intel Macs in Firefox and Windows-on-ARM Chrome. Measured coverage is about 83-89% of users, so a production app in late 2026 still needs a WebGL 2 path (or an honest "not supported" state) for roughly one visitor in six to nine.

- Chromium (Chrome, Edge): shipped on Mac, Windows x86/x64 and ChromeOS in 113; on Android 12+ with ARM/Qualcomm/Intel GPUs in 121 and Imagination GPUs on Android 16+ in 139; Samsung Xclipse and other Android GPUs are still listed as to-be-done; Linux has Intel Gen12+ in 144 and NVIDIA (driver 535.183.01+) on Wayland in 147, with other Linux GPUs behind flags; Windows ARM64 is behind a flag. Page last edited 2 Oct 2026 — [gpuweb Implementation Status wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- Firefox: shipped on Windows in 141; macOS Apple Silicon in 145 (macOS 26+) and 147 (all macOS versions); Intel Macs are Nightly-only; Linux is Nightly-only with Mozilla expecting to ship in 2026; Android is behind a flag with work expected in 2026 — [gpuweb Implementation Status wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- Safari: enabled by default in Safari 26 on macOS Tahoe 26, iOS 26, iPadOS 26 and visionOS 26 — [gpuweb Implementation Status wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- The four Firefox releases after that wiki edit do not announce WebGPU on Linux, Android or Intel Macs: 157 (29 Sep 2026), 158 (13 Oct 2026), 159 (27 Oct 2026), 160 (10 Nov 2026) — [Firefox 157 notes](https://www.firefox.com/en-US/firefox/157.0/releasenotes/); [Firefox 158 notes](https://www.firefox.com/en-US/firefox/158.0/releasenotes/); [Firefox 159 notes](https://www.firefox.com/en-US/firefox/159.0/releasenotes/); [Firefox 160 notes](https://www.firefox.com/en-US/firefox/160.0/releasenotes/)

Secondary source, not checked against caniuse history — [enterno.io](https://enterno.io/en/s/research-webgpu-adoption-browsers-2026)

- Default device limits that matter for large data: `maxStorageBufferBindingSize` 128 MiB, `maxBufferSize` 256 MiB, `maxTextureDimension2D` 8192, `maxStorageBuffersPerShaderStage` 8, `maxUniformBufferBindingSize` 64 KiB; higher values are requested through `requiredLimits` after checking the adapter — [MDN GPUSupportedLimits](https://developer.mozilla.org/en-US/docs/Web/API/GPUSupportedLimits)
- How shipped projects handle fallback: three.js `WebGPURenderer` falls back automatically to a WebGL 2 backend and can be forced to it with `forceWebGL` — [three.js manual](https://threejs.org/manual/pages/webgpurenderer.html). deck.gl keeps WebGL 2 as the default and describes WebGPU as work in progress and not ready for production — [deck.gl WebGPU guide](https://deck.gl/docs/developer-guide/webgpu). PlayCanvas falls back to WebGL 2 and cites about 85% WebGPU coverage (search-result summary of its blog) — [PlayCanvas blog](https://blog.playcanvas.com/new-in-supersplat-webgpu-and-streaming-bring-huge-performance-wins)
- Regression risk is real: a three.js forum thread from November 2025 reports that Firefox 145 broke three.js WebGPU and TSL while Nightly still worked (search-result summary) — [three.js forum](https://discourse.threejs.org/t/new-firefox-version-145-broken-three-js-webgpu-and-tsl/88092.md)

### Inferences
- "Enabled by default" overstates real coverage: the Web3DSurvey figure counts a working adapter and is 4-6 points below caniuse; Linux is the standout hole (about 18% success), followed by Android (about 70%).
- The users who will not get WebGPU in late 2026 are: almost everyone on Linux outside Chrome with Intel Gen12+/NVIDIA-Wayland, Firefox on Android and Intel Macs, Chrome on Windows ARM64, Android below 12 or with unsupported GPUs, and Apple devices that cannot run OS 26.
- Recommended fallback design (opinion): feature-detect with `navigator.gpu.requestAdapter()` (it can return null on blocklisted hardware even where the API exists); keep one scene description that runs on WebGL 2 (instancing plus data textures, no compute dependency) and treat WebGPU-only work (compute culling, large storage buffers) as progressive enhancement; show a static image or 2D list when neither works.
- The 128 MiB default storage-buffer binding limit means large geometry tables must either request higher limits or be chunked, which is one more reason to stream geometry by level of detail instead of uploading everything.
- Chrome's compatibility mode is opt-in and Android-first, so it does not yet close the Linux or old-desktop gap.

### Gaps
- No dated announcement of Firefox WebGPU on Linux or Android was found; the wiki only says "2026" and Firefox 157-160 notes are silent.
- The caniuse Firefox row conflicts with the implementation-status wiki; caniuse may be encoding per-OS partial support in a way the retrieval flattened. Not resolved.
- No source quantifies what share of Android devices fall outside the supported GPU list, or how many Intel Macs can run Safari 26.
- Web3DSurvey gives no collection window and its sample is visitors to 3D sites, so it may over- or under-state general coverage.
- Standardisation status of multi-draw indirect could not be confirmed beyond its absence from recent Chrome notes.

## 2. Three.js, react-three-fiber, drei and the alternatives

### Takeaway
three.js r187 (30 Oct 2026) is where all new renderer work happens through `WebGPURenderer` and TSL, with compute shaders and a new post-processing stack, but the official manual still describes the renderer as experimental and a high-priority issue about slow many-draw-call scenes has been open since February 2025. React-three-fiber stable is v9.8.2 (React 19); the WebGPU-first v10 is still alpha, as is drei 11. For a scene made of a few instanced draw calls the stack is workable today; for thousands of separate meshes it is measurably slower than the old WebGL renderer.

### Cited Findings

- Recent three.js releases: r185 (1 Jul), r186 (24 Sep), r187 (30 Oct). r185 added surfacing of uncaptured GPU errors and WGSL diagnostics, WebXR in WebGPURenderer, `storageTexture3D` and instanced meshes with render bundles; r186 added `compileComputeAsync()`, `DirectRenderPipeline`, compute `updateBefore`/`updateAfter` hooks and better tree-shaking; r187 added `ProxyNodeMaterial`, parallel pipeline compilation in `compileAsync()`, depth-only render targets and several `BatchedMesh` fixes — [three.js releases](https://github.com/mrdoob/three.js/releases)

- Known performance pitfall (open, labelled high priority): each object has its own uniform buffer, so scenes with many render items are slow. Reported numbers: 20,000 non-instanced cubes at about 60 fps on WebGLRenderer versus about 15 fps on WebGPURenderer (M1 Pro, r173, Feb 2025); in January 2026 a maintainer measured the WebGL 2 backend at about 12 fps versus 60 fps in Chrome and 19 versus 57 on a Pixel 8a; on 15 Sep 2026 a user measured r186's WebGL 2 fallback at about 31% slower CPU submit with about 80% more GL calls — [three.js issue #30560](https://github.com/mrdoob/three.js/issues/30560)
- Independent report on r183 (Chrome 148, RTX 4090 laptop, 4,000 meshes, about 8M triangles): CPU render 4.5 ms on WebGLRenderer, 9.7 ms on WebGPURenderer, 10.3 ms with `forceWebGL`; cold first frame 32 ms, 167 ms and 344 ms respectively. The author paused a port until the renderer matures — [three.js forum, May 2026](https://discourse.threejs.org/t/webgpurenderer-2x-slower-cpu-and-5-10x-slower-first-frame-than-webglrenderer-on-many-mesh-scenes-r183-same-on-both-backends/91904)
- Instancing removes the gap: on r186.1 (RTX 5070 Ti, Chromium 155, 1280x720) an `InstancedMesh` of a 6,056-triangle model ran at the 60 fps cap for 1,000 and 10,000 instances on classic WebGL, native WebGPU and the WebGL 2 backend alike, and at about 20 fps for 100,000 instances (about 606M triangles submitted) on all three. The same test showed `BatchedMesh` reporting 1 render call on classic WebGL but 1,001 on native WebGPU for 1,000 objects — [three.js forum benchmark, Oct 2026](https://discourse.threejs.org/t/three-js-plant-instancing-benchmark-240-desktop-samples-csv-json-and-a-standalone-harness/95719)

### Inferences
- Maturity assessment (opinion grounded in the evidence above): `WebGPURenderer` plus TSL is a reasonable choice for a new renderer whose frame is a handful of instanced or compute-driven draw calls, and a poor choice if the design keeps thousands of individual `Mesh` or `Line` objects. The current app's 108 draw calls are harmless either way; scaling that design to 20,000 objects is what would hurt.
- Choosing `WebGPURenderer` means writing every custom shader once in TSL and getting WGSL and GLSL from it, but it also means giving up the GLSL ecosystem (drei shader materials, pmndrs `postprocessing`, `EffectComposer`). Mixing the two renderers doubles shader work, so pick one per canvas.
- The stable React path today is R3F v9 with an async `gl` factory that returns an initialised `WebGPURenderer`; v10 and drei 11 are alpha and should not anchor a build that needs to be dependable, but the app should isolate renderer access so the later `state.gl` to `state.renderer` rename is cheap.
- Pin three.js exactly and upgrade deliberately: the renderer changes every release, a single Firefox release broke it in 2025, and the R3F alphas already require recent three versions.
- A scene graph is not required for the atlas itself. A thin custom renderer (raw WebGPU with TypeGPU, or luma.gl) for the 20,000 to 1M object layer, hosted inside React, is a defensible alternative; the counter-argument is that AI coding agents are far more fluent in three.js than in raw WebGPU (opinion).
- Alternatives in one line each (opinion): Babylon.js is the most complete engine with first-class WebGPU but is heavier and less idiomatic in React; PlayCanvas has the most advanced shipped GPU-driven pipeline (for splats) and is MIT; Rust plus wgpu compiled to WebAssembly gives maximum control at the cost of iteration speed for a solo developer; Threlte only makes sense if the app moves to Svelte.

### Gaps
- Only the first part of the three.js release notes page could be read; r187 post-processing changes and anything beyond the first 100,000 characters are not covered.
- No statement was found of when `WebGPURenderer` will stop being labelled experimental, or when issue #30560 will be fixed.
- Whether TSL compute nodes run on the WebGL 2 backend, and with what limits, was not verified from a primary source.
- No release date exists for R3F v10 or drei 11 stable.
- The Babylon.js 9 announcement page itself could not be fetched (redirect); its feature list here comes from a search summary.

## 3. Techniques for drawing ten thousand to a million protein-like objects

### Takeaway
The recipe is proven in molecular graphics: store each shape once, draw with GPU instancing, switch representation by distance (points, then impostors or simplified shapes, then real geometry), and cull by frustum and occlusion. Mol* Mesoscale Explorer uses exactly this to keep scenes of up to three billion atoms interactive in a browser. For backbone ribbons specifically, generating tube or ribbon geometry in the vertex shader from control points held in a data texture or storage buffer is an established pattern, with one known trap (per-vertex frames cannot be computed sequentially on the GPU).

### Cited Findings
- Mesoscale Explorer (Mol*-based web app): each molecular entity's coordinates are uploaded once and drawn many times with per-instance transforms; atoms are ray-cast sphere impostors; detail drops with camera distance; structures outside the frustum or fully occluded are skipped; four presets (Ultra, Quality, Balanced, Performance) trade detail for frame rate; screen-space ambient occlusion and contact shadows provide depth. The default Quality preset gave interactive performance for all tested models, including those with up to 3 billion atoms, measured at 1598x1776 on a Threadripper 1950X with a Quadro RTX 8000 and on an Apple M1 — [bioRxiv full text](https://www.biorxiv.org/content/10.1101/2024.09.02.610826v1.full); [Protein Science via PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC11409463/); [UCSF journal-club notes](https://www.cgl.ucsf.edu/home/meng/jclub/mesoscale.html)
- Mol* keeps adding the same class of optimisation in 2026: v5.10.0 (14 Jun) an instance-granularity memory guard and Morton-ordered sphere LOD; v5.12.0 (28 Sep) merging of representation render objects to cut draw calls; v5.13.0 (4 Oct) hover and selection marking separated from scene rendering so they no longer trigger a full re-render; the unreleased section adds GPU-side culling on WebGPU (automatic from 20,000 instances) with occlusion tested against the previous frame's depth — [Mol* changelog](https://github.com/molstar/molstar/blob/master/CHANGELOG.md)
- cellVIEW (2015) reached 60 Hz on virus- and bacterium-scale datasets by storing each molecule type once and instancing it, using level of detail both for speed and to reduce clutter, and generating DNA strands procedurally on the GPU (search-result summary) — [cellVIEW, TU Wien](https://cg.tuwien.ac.at/research/publications/2015/cellVIEW_2015)
- A 2025 survey-style paper notes that static scenes of up to a billion atoms in Mol* and YASARA are made possible by instancing (search-result summary) — [VTX paper, arXiv](https://www.arxiv.org/pdf/2503.07181)
- Vertex-shader tubes: a September 2026 Codrops article on lit GPU tubes in TSL explains that `TubeGeometry` builds frames by parallel transport, which is sequential (each frame needs the previous one) and therefore unavailable to a vertex shader; its approach treats the curve as a function of a parameter and notes the position could equally be a spline read from a storage buffer (search-result summary; the article itself refused automated fetching) — [Codrops](https://tympanus.net/codrops/2026/09/07/drawing-with-light-an-exploration-of-lit-gpu-tubes-with-tsl-and-webgpu/)
- Related patterns with working examples: evaluating parametric curves in the vertex shader over a reused cylinder grid to animate thousands of curves (with the caveat that frustum culling must be disabled or bounds fixed because the base geometry carries no real positions); per-instance lookups with `texelFetch` into a `DataTexture`; a "vertexless" line built from instanced geometry plus a data texture; and Troika's `BezierMesh`, which bends a tube on the GPU (search-result summaries) — [parametric curves article](https://frontendfoc.us/link/15952/web); [three.js forum: fat lines with texelFetch](https://discourse.threejs.org/t/tetrahedra-fat-lines-batching-texelfetch/43702); [three.js forum: vertexless line](https://discourse.threejs.org/t/vertexless-line-instancedbuffergeometry-datatexture/46016.md); [Troika BezierMesh](https://cdn.jsdelivr.net/npm/troika-three-utils@0.52.4/docs/BezierMesh.md)
- TSL exposes what the pattern needs (`instanceIndex`, `vertexIndex`, `textureLoad`, `storage`, `instancedArray`, `positionNode`) — [TSL wiki](https://github.com/mrdoob/three.js/wiki/Three.js-Shading-Language)
- Throughput reference: 100,000 instances of a 6,056-triangle mesh (about 606M triangles per frame) ran at about 20 fps on an RTX 5070 Ti regardless of backend; 10,000 instances (about 61M triangles) held the 60 fps cap — [three.js forum benchmark](https://discourse.threejs.org/t/three-js-plant-instancing-benchmark-240-desktop-samples-csv-json-and-a-standalone-harness/95719)
- Point-layer reference: deck.gl reports about 60 fps up to roughly 1M scatterplot items and 10-20 fps at about 10M on a 2015 MacBook Pro; most layers crash somewhere between 10M and 100M items because of allocation limits; overdraw dominates (a 5-pixel-radius point costs about 100 fragments, so 10M points can mean a billion fragments per frame); high-DPI rendering quadruples fragment work — [deck.gl performance guide](https://deck.gl/docs/developer-guide/performance)
- Billboard impostors and atlases: an octahedral-impostor library for three.js demonstrated 200,000 trees on a 3072x3072 terrain with mobile as a target; a 2026 blog series on scaling to a million impostors found per-frame CPU work becomes the bottleneck and moved updates to the GPU, and warns that three.js frustum-culls the whole batch if the bounding sphere is left at the unit quad (search-result summaries) — [three.js forum](https://discourse.threejs.org/t/a-forest-of-octahedral-impostors/85735); [open-world browser series](https://app.cinevva.com/blog/2026-05-04-open-world-browser-part-19-imposters)
- Ready-made instancing with culling and LOD: `InstancedMesh2` (`@three.ez/instanced-mesh`, MIT, 0.3.16 with a 1.0 beta on 2026-11-04) offers per-instance frustum culling, an optional BVH, per-instance LOD, sorting, per-instance uniforms and a million-tree example; its README does not state WebGPURenderer support — [InstancedMesh2](https://github.com/agargaro/instanced-mesh); [npm](https://registry.npmjs.org/@three.ez/instanced-mesh)
- GPU-driven culling in the browser exists but is still demo-grade: luma.gl has a GPU frustum-culling example; VTK implements two-pass hierarchical-Z occlusion culling with WebGPU compute (depth mip chain rebuilt each frame, not available on its OpenGL backend); a "nanite" WebGPU demo does per-instance and per-meshlet frustum and occlusion culling; another small engine writes only visible objects into an indirect draw buffer from a compute pass (search-result summaries) — [luma.gl example](https://luma.gl/next/examples/experimental/gpu-frustum-culling); [VTK occlusion culler](https://docs.vtk.org/en/latest/release_details/9.4/webgpu-occlusion-culler.html); [nanite-webgpu](https://github.com/Scthe/nanite-webgpu); [gfxlite](https://github.com/somepablo/gfxlite)
- GPU picking: the three.js forum points to the official `webgpu_multiple_rendertargets_readback` example; the classic approach renders IDs as colours and reads back the pixel under the cursor, optionally into a 1x1 target, which one thread found inconsistent across devices; luma.gl's index-picking target uses an integer ID attachment with a 256-byte readback to satisfy WebGPU row alignment (search-result summaries) — [three.js forum: picking in WebGPU](https://discourse.threejs.org/t/what-is-the-best-way-to-pick-in-webgpu/69973); [three.js forum: device inconsistency](https://discourse.threejs.org/t/gpu-picking-inconsistent-across-devices/12647); [luma.gl picking target](https://luma.gl/next/docs/api-reference/experimental/gpu-primitives/gpu-index-picking-target)
- Picking at scale in deck.gl: up to 16M distinguishable items per layer and 256 pickable layers; since 9.4 most layers pick using shader built-ins instead of picking-colour buffers, and picking is asynchronous on WebGPU — [deck.gl performance guide](https://deck.gl/docs/developer-guide/performance); [deck.gl what's new](https://deck.gl/docs/whats-new); [deck.gl WebGPU guide](https://deck.gl/docs/developer-guide/webgpu)
- Transparency: three.js sorts transparent objects back to front per object; object-level sorting cannot resolve intersecting or deeply overlapping surfaces and becomes the bottleneck at high depth complexity; weighted-blended order-independent transparency needs only multiple render targets and float textures and avoids sorting but is approximate; luma.gl ships a WBOIT renderer for WebGPU and WebGL 2; the `three-wboit` package targets WebGL (search-result summaries) — [three.js forum](https://discourse.threejs.org/t/instancedbuffergeometry-and-transparency/4722.md); [Transparency for 3D surfaces notebook](https://rreusser.github.io/notebooks/transparency-for-3d-surfaces); [Cesium on WBOIT](https://cesium.com/blog/2014/03/14/weighted-blended-order-independent-transparency/); [luma.gl WBOIT renderer](https://luma.gl/next/docs/api-reference/experimental/wboit-renderer); [three-wboit](https://www.github.com/stevinz/three-wboit)
- Embedding Atlas renders points with order-independent transparency in its fragment shader — [Embedding Atlas paper](https://arxiv.org/html/2505.06386)
- Blending is expensive even in 2D graph rendering: Sigma v4's guide recommends a solid colour close to the background instead of opacity below 1, and reports up to about 80% frame-time reduction from opacity and antialiasing changes against about 6% from halving vertex count — [Sigma performance guide](https://www.sigmajs.org/how-to/technical/performance/)
- Bloom and post-processing cost: the three.js bloom pass already blurs at half resolution; an Arm article (2018) puts mobile bloom at about 3 ms and notes mobile GPUs handle multiple dependent passes poorly; a Babylon.js forum answer notes bloom processes the full image three times and suggests lowering resolution; deck.gl's post-process effect is not supported on WebGPU; Mol* v5.11.0 added bloom for transparent and emissive geometry (first three are search-result summaries) — [three.js forum](https://discourse.threejs.org/t/solved-why-the-image-looks-so-low-res-after-applied-unrealbloompass/17361); [Arm blog](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/post-processing-effects-on-mobile-optimization-and-alternatives); [Babylon.js forum](https://forum.babylonjs.com/t/bloom-makes-gpu-usage-extremely-high/26703); [deck.gl WebGPU guide](https://deck.gl/docs/developer-guide/webgpu); [Mol* changelog](https://github.com/molstar/molstar/blob/master/CHANGELOG.md)

### Inferences
- A four-level design fits the evidence (proposal):
  - Level 0, everything as points: one instanced draw call for all N proteins, sized and coloured from a compact attribute buffer. 570,000 points at 16 bytes each is about 9 MB, and both Embedding Atlas (4M points at 60 fps on an M1 Pro) and deck.gl (1M at 60 fps on 2015 hardware) show this is comfortably within budget.
  - Level 1, a recognisable glyph for the few thousand proteins nearest the camera: either a pre-rendered sprite atlas of each fold's silhouette, or a very low-resolution ribbon from 8-16 control points. A single 8192x8192 atlas (the default WebGPU texture limit) holds 16,384 sprites at 64x64, so 20,000 proteins need two atlases; 570,000 would need tile-streamed atlases, which favours the procedural low-resolution ribbon at that scale.
  - Level 2, real alpha-carbon backbone for the tens to hundreds of proteins that are large on screen: one shared strip or ring-segment geometry instanced per backbone segment; the vertex shader reads four neighbouring control points by index, evaluates a Catmull-Rom spline and offsets by a frame. To avoid the sequential-frame problem, precompute normals offline (parallel transport at build time) and store them beside the control points, or use a camera-facing ribbon whose shading normal is derived from the across-ribbon coordinate (a tube impostor at 2 triangles per residue instead of roughly 16 for an 8-sided tube).
  - Level 3, hand-off to Mol* for one protein with full atoms.
- Budget arithmetic (researcher's calculation, assuming roughly 20,000 human proteins averaging about 560 residues): about 11M alpha carbons. As a camera-facing ribbon that is about 22M triangles if everything were drawn at Level 2, which the instancing benchmark suggests a desktop discrete GPU can do at 60 fps but an integrated GPU or phone cannot, so LOD selection by projected size is mandatory, not optional. Control points as normalised 16-bit integers plus one byte of pLDDT come to roughly 80 MB uncompressed for the human proteome, inside the 128 MiB default storage-buffer binding if split sensibly. For Swiss-Prot scale (570,000 entries) full backbones exceed a gigabyte and must be streamed by spatial tile and level rather than loaded up front.
- This design is WebGL 2-compatible: instancing, integer vertex and instance IDs and `texelFetch` on data textures all exist there, so compute shaders are an optimisation (GPU culling into an indirect buffer) rather than a requirement. That matches the fallback advice in section 1.
- Culling: for 20,000 objects a CPU test of bounding spheres against the frustum each frame (or a grid/BVH) is trivial; at 570,000 or more use spatial tiles and only test tiles, or move the test to a compute pass on WebGPU. Occlusion culling is unlikely to pay off in a sparse embedding-style layout (opinion).
- Picking: for the point level, CPU picking against a spatial index is simpler than a readback and has no latency; for ribbons, write an integer ID to a second render target and read back one pixel asynchronously on pointer move, throttled. Expect the readback to be asynchronous on WebGPU.
- Transparency and glow: keep the bulk opaque. Use additive blending for point glow (order-independent by construction) and reserve true alpha for a handful of highlighted objects. Run bloom at half or quarter resolution on an emissive-only target, cap device pixel ratio at about 1.5-2, and switch bloom off on low tiers.
- The existing implementation (one line object per protein) should be replaced by a single instanced draw per level; that is the change that makes 20,000 feasible.

### Gaps
- No published benchmark was found for instanced vertex-shader tubes or ribbons at the 10,000+ protein scale; the budget above is extrapolated from a foliage benchmark and from molecular viewers that draw spheres.
- The Mesoscale Explorer paper's frame-time and loading numbers are in a figure and could not be extracted as text.
- No measurement of bloom or other post-processing cost under `WebGPURenderer` was found; the cited numbers are WebGL-era or mobile-engine figures.
- No source evaluates pre-rendered sprite atlases for protein structures specifically.
- The Codrops article could not be read directly, so its technique is described from a search summary.

## 4. Large point-cloud and embedding-map technology

### Takeaway
For 20,000 to a few million points no tiling is needed and several maintained, permissively licensed renderers exist. Apple's Embedding Atlas (MIT, v0.26.0) is the most complete embedding-map product (density contours, automatic cluster labels, cross-filtering over DuckDB, 4M points at 60 fps on an M1 Pro) but is 2D and WebGPU-only since August 2026. deck.gl 9.4 is the most general toolkit, with WebGPU still experimental. regl-scatterplot is the lightest 2D option. cosmos.gl v3 and Sigma v4 (both MIT) cover graphs. Nomic's deepscatter is non-commercial and stale.

### Cited Findings
- Embedding Atlas: MIT; npm package `embedding-atlas` 0.26.0 (2026-10-15) with `EmbeddingAtlas` and `EmbeddingView` components and React and Svelte entry points; features are automatic clustering and labelling, kernel-density contours, real-time search and nearest neighbours, cross-filtered charts, and an MCP interface; the README claims smooth performance up to a few million points on WebGPU — [Embedding Atlas README](https://raw.githubusercontent.com/apple/embedding-atlas/HEAD/README.md); [npm](https://registry.npmjs.org/embedding-atlas)

### Inferences
- At 20,000 to 570,000 points a single binary buffer is enough; tiles and quadtrees only become necessary around 10M points and above, where single-buffer renderers start to fail.
- All the mature embedding-map tools are 2D. A 3D UMAP cloud is harder to read and navigate than a 2D map (opinion), and every reference product (Embedding Atlas, Nomic Atlas, WizMap) chose 2D. A defensible compromise is a 2D layout rendered in a 3D scene so that the camera can tilt and proteins can rise out of the plane when zoomed in.
- Embedding Atlas is the strongest design reference even if it is not embedded: density contours instead of raw overplotting, automatically placed cluster labels that behave like map labels, and cross-filter charts driven by SQL. Its `EmbeddingView` could be embedded for a "map" mode, with the caveat that it now fails on any browser without WebGPU.
- Cluster labels for proteins can be computed at build time (majority family, domain or GO term per density cluster) and shipped as static JSON, avoiding any runtime clustering.
- For the knowledge graph, Sigma v4 or cosmos.gl v3 (both MIT) replace the current force-graph component cleanly; Cosmograph's non-commercial licence is acceptable for a non-commercial portfolio but constrains later reuse.

### Gaps
- No independent, like-for-like benchmark across these libraries was found; every number above is self-reported.
- Mobile performance of Embedding Atlas and of deck.gl on WebGPU is undocumented.
- Whether cosmos.gl plans a WebGPU backend is not stated in the v3 announcement.
- The current rendering engine behind Nomic Atlas (as opposed to the stale open-source deepscatter) is unknown.

## 5. Mol*: version, WebGPU, integration, MolViewSpec, themes and alternatives

### Takeaway
Mol* 5.13.1 (8 Oct 2026, MIT) remains the standard web molecular viewer and ships a release roughly every month. Released versions render with WebGL; WebGPU appears only in the unreleased changelog (GPU culling), and a v6 prototype reorganises the library into native-ESM workspace packages. The supported integration is the npm package with either the built-in React UI or a headless `PluginContext`, not a script tag. MolViewSpec v1 gives declarative, shareable scenes with per-residue colouring from external annotations and multi-scene stories. A pLDDT colour theme using the AlphaFold palette is built in.

### Inferences
- Replace the side-loaded script with a dynamic import of the npm package in a lazily loaded client-only chunk; at about 1.3 MB compressed it must stay off the initial route.
- For a premium interface, use the headless `PluginContext` and build the surrounding controls in the app's own design system, reusing only specific Mol* panels (for example the sequence view) where they earn their place (opinion). If the built-in UI is used, `renderReact18` relies on the modern root API and probably works under React 19, but that is undocumented and must be tested.
- Keep one Mol* instance mounted for the life of the session and swap structures, rather than creating and destroying viewers, to avoid WebGL context churn next to the atlas canvas.
- Per-residue themes such as AlphaMissense are easiest as MolViewSpec annotations generated client-side from the app's own data, or as a custom colour theme modelled on the built-in pLDDT provider.
- Build the PAE heatmap in-house: it is a single N-by-N image with a legend and a linked hover, and no maintained component exists to adopt.
- The AlphaFold four-colour pLDDT palette is the recognisable convention and should be the default; see section 11 for its limitations on dark backgrounds.

### Gaps
- No official statement on React 19 support or on Vite configuration for Mol* was found.
- No timeline for WebGPU in a Mol* release or for v6.
- Whether Mol* itself offers a PAE plot UI (as opposed to parsing pairwise metrics) was not confirmed.
- No measurements for loading many AlphaFold structures at once, and no source for browser limits on simultaneous WebGL contexts.

## 6. Sequence, variant and genome track components

### Takeaway
For protein-coordinate tracks the maintained standard is EMBL-EBI's Nightingale (custom elements, MIT, 5.11 with v6 prepared) and the UniProt viewer built on it, `protvista-uniprot` 5.0.0 (23 Nov 2026). JBrowse 2 and igv.js are genome-coordinate tools and heavy for a protein-first app, though JBrowse's protein-structure and alignment plugins are actively released. ## 7. In-browser data: DuckDB-WASM, Arrow, Parquet readers, SQLite and static hosting

### Takeaway
A fully static data layer is realistic. DuckDB-WASM now tracks DuckDB 2.0.1 but is published on npm as rolling dev builds, is single-threaded by default, capped at 4 GB and costs about 6 MB of compressed WebAssembly before extensions, so it should be lazy-loaded for analytics rather than used for every lookup. hyparquet (pure JavaScript, MIT, no dependencies) reads Parquet over HTTP range requests at a tiny fraction of that size. The hosting detail that decides the design: Cloudflare's free static-asset hosting ignores Range headers, whereas R2 supports them with free egress.

### Cited Findings
- DuckDB itself: 1.4.0 LTS (16 Sep 2025, end of life 17 Nov 2026), 1.5.0 (9 Mar 2026), 2.0.0 LTS "Cinnamon Teal" (21 Oct 2026), 2.0.1 LTS (20 Nov 2026) — [DuckDB release calendar](https://duckdb.org/release_calendar)

### Inferences
- Proposed split (opinion): a small "core" table (one row per protein, a few megabytes) loaded eagerly as Arrow or Parquet straight into typed arrays for the renderer; large per-residue and per-variant tables as Parquet sorted by accession with small row groups, read on demand by hyparquet through range requests; DuckDB-WASM loaded only when the user opens an analytical feature (cross-filtering, ad-hoc SQL); results and fetched ranges cached in the Cache API or OPFS.
- Put anything that needs range requests on R2 behind a custom domain, not in the static-asset bundle. Ten million free Class B operations a month is far more than a portfolio project will use, and cached responses at the edge should not count against it (not verified).
- Parquet layout is the performance lever: sort by the lookup key, keep row groups to a few thousand rows and write statistics, so that a protein's residues are one or two range requests.
- Pin DuckDB-WASM to an exact version: the `latest` tag is a dev build and extension binaries are version-specific.
- Do not plan on a DuckDB vector-search extension in the browser; section 8 shows brute force is enough at this scale.
- With a 4 GB ceiling and one thread, Swiss-Prot-scale per-residue data must stay in remote Parquet and be queried lazily, never materialised in the browser.

### Gaps
- No 2026 benchmark of DuckDB-WASM or hyparquet reading Parquet over range requests was found; guidance above is architectural, not measured.
- Whether Cloudflare's cache serves partial content correctly for cached R2 objects on a custom domain was not verified.
- The R2 pricing page does not say explicitly how range reads are counted.
- OPFS storage quotas (especially on Safari) and the status of 64-bit WebAssembly memory for DuckDB-WASM were not checked.
- Bundle variants beyond `eh`, `mvp` and `coi` and their thread requirements are not described in the current docs pages retrieved.

## 8. WebAssembly and in-browser machine learning

### Takeaway
Rust-to-WebAssembly tooling is healthy again under a new organisation, SIMD and threads are available to about 97% of users, but threads require cross-origin isolation headers and a nightly Rust toolchain, so they should be avoided unless necessary. Transformers.js v4 and ONNX Runtime Web run ESM-2 protein language models in the browser, with the 8M and 35M checkpoints small enough to ship (8-35 MB quantised). The specialised structure tools (Foldseek, Foldcomp, TM-align) have no maintained browser builds. Brute-force search over quantised vectors is fast enough for 570,000 items, so approximate indexes are unnecessary.

### Cited Findings
- Rust tooling: the Rust project announced on 21 Jul 2025 that the rustwasm GitHub organisation would be archived, with wasm-bindgen moving to its own organisation and tools such as wasm-pack slated for archiving unless maintainers claimed them — [Inside Rust blog](https://blog.rust-lang.org/inside-rust/2025/07/21/sunsetting-the-rustwasm-github-org/). As of this research wasm-pack lives under the wasm-bindgen organisation, is not archived, names a maintainer, and published 0.15.1 on 2026-10-30 — [wasm-pack repository](https://github.com/rustwasm/wasm-pack); [npm](https://registry.npmjs.org/wasm-pack)
- Threads in Rust WebAssembly (wasm-bindgen-rayon): Rayon on Web Workers sharing one memory through `SharedArrayBuffer`; requires cross-origin isolation, a nightly toolchain (tested with a November 2025 nightly), atomics and bulk-memory target features and a rebuilt standard library; works with webpack 5, Parcel 2 and Vite; shipping a second non-threaded build chosen by feature detection is the suggested fallback — [wasm-bindgen-rayon](https://github.com/RReverser/wasm-bindgen-rayon)
- Availability: WebAssembly SIMD 96.78% of global usage (Chrome 91, Firefox 89, Safari 16.4); threads and atomics 97.18% (Chrome 74, Firefox 79, Safari 14.1) — [caniuse wasm-simd](https://caniuse.com/wasm-simd); [caniuse wasm-threads](https://caniuse.com/wasm-threads)
- Setting isolation headers on static hosts: Cloudflare static assets accept a `_headers` file (up to 100 rules) but those headers are not applied to Worker-generated responses; GitHub Pages documents no way to set custom headers; the service-worker workaround package `coi-serviceworker` has not been updated since July 2023 — [Cloudflare static assets headers](https://developers.cloudflare.com/workers/static-assets/headers/); [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits); [npm coi-serviceworker](https://registry.npmjs.org/coi-serviceworker)
- Bioinformatics tools already compiled for the browser (biowasm, run through Aioli 3.2.4, published 2026-10-26): samtools 1.21, bcftools, bedtools, MAFFT 7.520, MUSCLE 5.1.0, Kalign 3.3.1, FastTree 2.2.0, HMMER 3.4, BLAST 2.17.0, DIAMOND 2.2.8, minimap2 and others. Foldseek, MMseqs2, TM-align/US-align and DSSP are not in the list — [biowasm CDN listing](https://biowasm.com/cdn/v3/); [npm aioli](https://registry.npmjs.org/@biowasm/aioli)
- Structure-alignment builds on npm are stale: `tmalign-wasm` 0.0.6 (2023-01-30) and `pulchra-wasm` 0.0.3 (2023-09-15); no packages named `foldcomp`, `foldcomp-wasm` or `usalign-wasm` exist — [npm tmalign-wasm](https://registry.npmjs.org/tmalign-wasm); [npm pulchra-wasm](https://registry.npmjs.org/pulchra-wasm)

### Inferences
- Researcher's own micro-benchmark (plain single-threaded JavaScript, Node 20 on an Apple M3 Pro, no WebAssembly or SIMD; indicative only): a full scan with top-k selection took 11 ms for 20,000 x 384-dimension 8-bit vectors; 32 ms for 20,000 x 1,280; 282 ms for 570,000 x 384; 975 ms for 570,000 x 1,280. Binary vectors with Hamming distance took 2 ms for 20,000 x 1,280 bits; 33 ms for 570,000 x 384 bits; 59 ms for 570,000 x 1,280 bits; 114 ms for 2 million x 384 bits.
- Therefore: at 20,000 proteins any representation is instant; at 570,000 a binary scan (27-91 MB in memory) followed by rescoring a few dozen candidates is interactive without any index, and WebAssembly SIMD or a WebGPU compute pass would only make it faster. Stale HNSW libraries are not needed.
- Even simpler for "similar proteins": precompute the k nearest neighbours offline and ship them as a column; then no runtime vector maths is needed except for user-supplied sequences.
- Embedding a pasted sequence in the browser is feasible with ESM-2 8M or 35M (8-35 MB quantised, cached after first use); the 150M model is borderline for casual visitors and 650M is impractical. The precomputed corpus must use the same model and pooling, and small-model embeddings are a weak proxy for structural similarity (opinion).
- Avoid a hard dependency on cross-origin isolation in the first release: it complicates every cross-origin resource (data on R2, embedded content) and is only needed for multi-threaded WebAssembly. DuckDB-WASM, ONNX Runtime Web and SQLite's pooled OPFS mode all run without it.
- In-browser Foldseek search is not realistic; pairwise structural alignment of two selected proteins is, but would mean compiling TM-align or US-align with Emscripten rather than adopting the stale packages.
- Since Foldcomp has no browser build, a purpose-built compact binary for backbone traces (quantised alpha-carbon coordinates plus pLDDT) is simpler than porting it, and is what the renderer needs anyway.
- Write WebAssembly modules in Rust with wasm-bindgen and wasm-pack only where JavaScript is measurably too slow (for example spline preprocessing or alignment); stable-toolchain SIMD is available, threads are not.

### Gaps
- No benchmark of ESM-2 inference speed under Transformers.js v4 with WebGPU was found, and the release notes do not mention protein models.

## 10. State management and URL-addressable state

### Takeaway
Two maintained approaches make application state fully addressable: nuqs 2.10 (typed search-param state for Next.js, React Router and plain React, with built-in throttling) and TanStack Router's validated, JSON-first search params that it explicitly positions as a state manager. Zustand 5.1 remains current and has a tiny, stable undo/redo middleware. The useful pattern is to separate shareable view state (URL), high-frequency transient state (never React or the URL) and document state (undoable, later collaborative).

### Cited Findings
- nuqs 2.10.3 (2026-11-10, MIT): updates replace the history entry by default and `push` is recommended only for navigation-like state; updates are client-only unless `shallow: false`; URL writes are throttled by default (50 ms, 120 ms in Safari) and configurable with throttle or debounce through `limitUrlUpdates`, while the returned state updates immediately; default values are removed from the URL by default; adapters accept global defaults and a middleware hook for the outgoing search params — [nuqs options](https://nuqs.dev/docs/options); [npm](https://registry.npmjs.org/nuqs)
- TanStack Router search params: each route validates and types its search params (Zod 4, Valibot, ArkType and other Standard Schema libraries work directly); parsing is JSON-first so nested objects and arrays survive while top-level keys stay readable; links and navigation take updater functions over the previous params; middlewares can retain params across links or strip defaults; the docs frame the URL as shareable, bookmarkable global state — [TanStack Router search params](https://tanstack.com/router/latest/docs/framework/react/guide/search-params)
- Store libraries: zustand 5.1.0 (2026-11-06); jotai 3.0.2 (2026-11-09); valtio 2.3.2 (2026-05-01); `@tanstack/store` 0.11.3 with its React binding at a 1.0 alpha (2026-11-23); `@preact/signals-react` 3.12.0 (2026-08-04); `@legendapp/state` still on 2.1.15 stable with v3 in beta — [npm zustand](https://registry.npmjs.org/zustand); [npm jotai](https://registry.npmjs.org/jotai); [npm valtio](https://registry.npmjs.org/valtio); [npm tanstack store](https://registry.npmjs.org/@tanstack/react-store); [npm signals](https://registry.npmjs.org/@preact/signals-react)
- Undo and redo: zundo is a sub-700-byte temporal middleware for Zustand (works with v4.2+ and v5) offering undo, redo, pause and resume, with options to track only part of the store, cap history, store diffs instead of snapshots and throttle recording; its last release was 2.3.0 on 2024-11-17 — [zundo repository](https://github.com/charkour/zundo); [npm](https://registry.npmjs.org/zundo)
- A sign of where React state is heading: React Flow 13 (November 2026) split its internal store into smaller stores with fine-grained subscriptions and is compiled with the React Compiler — [React Flow what's new](https://reactflow.dev/whats-new)

### Inferences
- Recommended state model (opinion):
  - View state in the URL: selected protein(s), camera pose, colour-by and filter settings, open panels, story step. Encode compactly (short keys; pack the camera's position and orientation into a short base64 string) and write on camera settle with a debounce of a few hundred milliseconds using history replace; push a history entry only for selection and navigation.
  - Transient state outside React and the URL: pointer hover, camera during motion and animation clocks belong in refs or non-reactive store subscriptions read inside the render loop.
  - Document state in a serialisable store slice: pinned items, annotations, workspace layout. This is what undo/redo tracks and what a collaboration layer would later synchronise.
- The same serialisable view-state schema can drive deep links, guided-story steps, undo and commands from the chat panel, which is worth designing once.
- Complex workspaces will outgrow comfortable URL lengths; either compress the state into the URL fragment or store it server-side and share a short id (which needs a write endpoint and therefore a little infrastructure).
- Zustand stays the pragmatic default for a react-three-fiber app (same maintainers, current release, transient subscriptions); with the React Compiler handling memoisation, the case for adopting signals is weaker than it was (opinion).
- If the app moves to TanStack Router, its search-param system can replace nuqs entirely.

### Gaps
- Zustand's documentation page on connecting state to the URL returned an error, so its recommended pattern was not reviewed.
- nuqs's documented URL-length guidance, parser catalogue and TanStack Router adapter were not on the page retrieved.
- What changed in Jotai 3 was not read.
- No comparative performance data for these stores in 2026 was found.

### Inferences
- What makes the admired work feel premium (opinion, synthesised from the references above rather than from designer write-ups):

- Stack suggestion (opinion): Tailwind 4.3, shadcn/ui components on Base UI, Motion for interface animation, GSAP only if timeline-style scroll scenes are needed. ### Inferences
- Cost of cursors and shared sessions on Cloudflare's free plan (researcher's arithmetic from the pricing above): five users sending cursor updates ten times a second for an hour produce 180,000 incoming messages, billed as 9,000 requests, so the 100,000-request daily allowance covers roughly eleven such room-hours per day. Casual multiplayer for a portfolio project is therefore free; sustained use needs the $5 plan and stays well inside $20.
- Throttle cursors to 10-15 updates per second and send camera poses only on change; with hibernation, idle rooms cost nothing.
- Liveblocks' free tier is adequate for a demo (ten people per room, about fifty user-hours a month) at the price of visible branding and a hosted dependency.
- Trystero is the only truly zero-infrastructure route and suits ephemeral "follow my view" sessions; reliability depends on public relays and on peers' network conditions, and nothing persists.
- tldraw's licence is a poor fit for an open-source, zero-budget project unless the free hobby licence is granted and its watermark accepted. An "infinite canvas workspace" for this app is arguably the 3D map itself plus floating panels; if a node-and-edge workspace is wanted, React Flow is the open choice (opinion).
- Sequence the work: make the document state serialisable first (section 10), add presence (cursors, selections, follow mode) second, and add shared editable state with Yjs on PartyServer only if the product needs it.

### Gaps
- tldraw's commercial price, and the exact terms and watermark rules of the hobby licence, are not public on the pages retrieved.
- React Flow Pro pricing and what it includes were not retrieved.
- How Liveblocks counts "collaboration minutes" for idle tabs was not examined.
- Per-object WebSocket connection limits on Durable Objects were not checked.

## 13. Scrollytelling, accessibility, performance budgets and CI testing

### Takeaway
Scroll-driven 3D stories no longer need a heavy library: native CSS scroll-driven animations reach about 89% of users (Firefox shipped them in October 2026) and GSAP's ScrollTrigger is free, while the older React scrollytelling helpers and Theatre.js have gone quiet. Canvas content is invisible to assistive technology by default, so accessibility has to be designed as a parallel DOM experience; one toolkit (Data Navigator) targets exactly this, and the react-three accessibility package is abandoned. Visual and performance testing of GPU rendering in CI is possible but constrained: screenshots vary by host and GPU, and hosted GPU runners are paid.

### Cited Findings
- CSS scroll-driven animations (`animation-timeline`): 89.12% of global usage; Chrome and Edge 115, Safari 26.0, Firefox 159 — [caniuse animation-timeline](https://caniuse.com/mdn-css_properties_animation-timeline). Firefox 159 (27 Oct 2026) lists scroll- and view-timeline support in its release notes — [Firefox 159 notes](https://www.firefox.com/en-US/firefox/159.0/releasenotes/)
- Scroll tooling status on npm: GSAP 3.15.1 (free, proprietary licence, see section 11); lenis 1.3.28 (2026-11-23, MIT) with a 2.0 in development; `@theatre/core` 0.7.2 with no release since May 2024; scrollama 3.2.0 unchanged since 2022; `@bsmnt/scrollytelling` last released February 2024; `@14islands/r3f-scroll-rig` last released December 2024 — [npm lenis](https://registry.npmjs.org/lenis); [npm theatre](https://registry.npmjs.org/@theatre/core); [npm scrollama](https://registry.npmjs.org/scrollama); [npm bsmnt scrollytelling](https://registry.npmjs.org/@bsmnt/scrollytelling); [npm r3f-scroll-rig](https://registry.npmjs.org/@14islands/r3f-scroll-rig)
- Motion uses native scroll timelines where available for scroll-linked animation — [Motion for React](https://motion.dev/docs/react)
- Domain-specific storytelling: MolViewSpec chains scenes into stories with animated transitions, and MolViewStories pairs each scene with Markdown narrative — [MolViewSpec docs](https://molstar.org/mol-view-spec-docs/); [MolViewStories docs](https://molstar.org/mol-view-stories/docs/)
- Canvas accessibility baseline: a canvas is a bitmap that exposes nothing about drawn objects; fallback content should be placed inside the element; MDN's general advice is to avoid canvas for content that must be accessible; iOS limits canvases to 4,096 x 4,096 pixels and exceeding a browser's maximum makes the canvas unusable — [MDN canvas element](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas)
- WCAG 2.2 success criterion 2.2.2 (Level A): moving content that starts automatically, lasts more than five seconds and is shown alongside other content needs a way to pause, stop or hide it, unless the movement is essential — [W3C Understanding 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
- React's view-transition component does not honour reduced-motion preferences automatically; the developer must handle it in CSS — [React ViewTransition reference](https://react.dev/reference/react/ViewTransition)
- Data Navigator (Carnegie Mellon, IEEE TVCG 2023, MIT): models a visualisation as a graph of nodes and edges for navigation and renders a layer of semantic HTML elements over SVG, canvas or WebGL, supporting keyboard, screen reader, touch, voice and custom input; framework-agnostic — [Data Navigator](https://dig.cmu.edu/data-navigator/)
- `@react-three/a11y` (focus, keyboard navigation, roles, screen-reader announcements and user-preference hooks for react-three-fiber) has had no release since 3.0.0 on 2022-05-15 — [react-three-a11y repository](https://github.com/pmndrs/react-three-a11y); [npm](https://registry.npmjs.org/@react-three/a11y)
- Automated accessibility checks: `@axe-core/playwright` 4.14.1 (2026-11-24) — [npm](https://registry.npmjs.org/@axe-core/playwright)
- Responsiveness budget: Interaction to Next Paint is good at 200 ms or less and poor above 500 ms at the 75th percentile; it measures clicks, taps and key presses (not scrolling or hovering) and is degraded by long main-thread tasks — [web.dev INP](https://web.dev/articles/inp)
- Rendering budgets from library guidance: high-DPI rendering produces four times the fragments and should be disabled when not needed; overdraw and blending dominate cost at scale — [deck.gl performance guide](https://deck.gl/docs/developer-guide/performance); [Sigma performance guide](https://www.sigmajs.org/how-to/technical/performance/)
- Visual regression: Playwright's `toHaveScreenshot` compares against stored references with pixelmatch (default per-pixel threshold 0.2, optional maximum differing pixels, custom stylesheet to hide volatile elements); rendering varies with host OS, hardware, settings and headless mode, so references must be generated and checked in the same environment; `@playwright/test` is at 1.65.1 — [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots); [npm](https://registry.npmjs.org/@playwright/test)
- GPU in headless Chrome: a Chrome team guide runs new-headless Chrome with Vulkan-backed ANGLE and the unsafe-WebGPU flag on a Linux machine with a real GPU (NVIDIA T4 or V100), verifies through `chrome://gpu`, and warns that with wrong drivers Chrome silently falls back to software rendering whose timings do not reflect real hardware — [Chrome: supercharge web AI testing](https://developer.chrome.com/blog/supercharge-web-ai-testing)
- CI cost: GitHub-hosted GPU runners cost $0.052 per minute (Linux, 4-core) and $0.102 (Windows), are not free for public repositories and require a Team or Enterprise plan; standard Linux is $0.006 per minute and standard macOS $0.062 — [GitHub Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)
- Instrumentation: Sigma exposes GPU timer queries and per-program draw statistics as debug settings; three.js r185 surfaces uncaptured GPU errors and shader diagnostics; `stats-gl` 4.2.3 (2026-07-10) is maintained while `r3f-perf` has not been released since November 2024 — [Sigma performance guide](https://www.sigmajs.org/how-to/technical/performance/); [three.js releases](https://github.com/mrdoob/three.js/releases); [npm stats-gl](https://registry.npmjs.org/stats-gl); [npm r3f-perf](https://registry.npmjs.org/r3f-perf)
- A reusable benchmarking protocol from the three.js community: fixed resolution and pixel ratio, at least five seconds and 300 frames of warm-up, 1,800 measured frame intervals, five repeats per configuration with alternating order, renderer counters reported separately from timings — [three.js forum benchmark](https://discourse.threejs.org/t/three-js-plant-instancing-benchmark-240-desktop-samples-csv-json-and-a-standalone-harness/95719)
- Transfer sizes that set the loading budget (Brotli): three.js core plus WebGPU renderer about 186 KB, Mol* viewer 1.31 MB, DuckDB-WASM 6.22 MB, ONNX Runtime WebGPU 4.82 MB — [jsDelivr three.core](https://cdn.jsdelivr.net/npm/three@0.187.0/build/three.core.min.js); [jsDelivr three.webgpu](https://cdn.jsdelivr.net/npm/three@0.187.0/build/three.webgpu.min.js); [jsDelivr molstar.js](https://cdn.jsdelivr.net/npm/molstar@5.13.1/build/viewer/molstar.js); [jsDelivr duckdb-eh.wasm](https://cdn.jsdelivr.net/npm/@duckdb/duckdb-wasm@1.33.1-dev57.0/dist/duckdb-eh.wasm); [jsDelivr ORT WebGPU wasm](https://cdn.jsdelivr.net/npm/onnxruntime-web@1.31.1/dist/ort-wasm-simd-threaded.jsep.wasm)

### Inferences
- Story architecture (proposal): a story is an ordered list of steps, each pairing narrative text with a view state in the same schema used for deep links; scroll progress interpolates the camera between steps while the canvas stays fixed behind the scrolling text. Drive it with native scroll timelines or ScrollTrigger; avoid the unmaintained helpers. The same step format serves guided tours, chat-driven "show me" commands and shareable links.
- Accessibility plan (proposal): give every visual view a DOM equivalent (a searchable, virtualised list or table and real HTML entity pages); provide keyboard navigation over a neighbour graph in the Data Navigator style, with arrow keys moving selection between nearby proteins and a live region announcing it; honour reduced-motion by replacing camera flights with cuts or fades and stopping idle rotation, which also satisfies the pause requirement; use colour-blind-safe palettes with a second encoding; put descriptive fallback content in the canvas.
- Performance budgets (researcher's proposal, not sourced targets): interactive shell before any 3D code; initial route JavaScript around 250-300 KB compressed with the renderer loaded immediately after; first map data within a few megabytes; Mol*, DuckDB and any model strictly lazy; 60 fps on Apple-silicon laptops and desktop discrete GPUs and at least 30 fps on integrated graphics and recent phones with pixel ratio capped; interaction latency at or under 200 ms.
- CI strategy within a zero budget (proposal): (1) unit-test the deterministic logic (level-of-detail selection, culling, URL encoding, data decoding); (2) run Playwright screenshots on the WebGL 2 path under software rendering with a fixed seed, frozen time, pixel ratio 1 and a tolerant threshold, to catch gross regressions rather than to judge quality; (3) assert renderer counters (draw calls, triangles, texture memory) along a scripted camera path, which is deterministic and needs no GPU; (4) measure real frame times on the developer's own machine using the forum protocol and commit the results, instead of paying for GPU runners.
- Expect headless WebGL and WebGPU to be the fragile part of CI; software fallback is slow and may be unavailable depending on flags, which is consistent with flakiness seen in headless end-to-end runs of WebGL apps generally.

### Gaps
- No authoritative published performance budgets for WebGL or WebGPU applications were found; the numbers above are the researcher's proposals.
- The current state of Chrome's software WebGL fallback policy in headless mode, and whether software WebGPU is usable in CI, were not verified.
- Whether GitHub's free macOS runners expose a usable GPU to headless browsers was not checked.
- No sourced example of a WebGL scene driven by native scroll timelines was collected, and Lenis and GSAP ScrollTrigger documentation were not reviewed in detail.
- No accessibility evaluation of an existing molecular or embedding viewer was found.
